第5章 データと秘密情報を守る：暗号化・ハッシュ・鍵

「暗号化しています」「ハッシュ化していました」はニュースでよく見ますが、それだけでは安全かどうか分かりません。この章では、ハッシュ・暗号化・エンコードの違い、通信と保存の暗号化、暗号ライブラリの正しい使い方、API キーやパスワードなどの秘密情報の置き場所、漏らしてしまったときの手順を扱います。暗号の理論は要りません。「どれを使い、どこに置くか」の正解を覚えれば足ります。

🧭この章で理解してほしいこと
  • ハッシュ・暗号化・エンコードは別物：ハッシュ＝戻せない、暗号化＝鍵で戻せる、エンコード＝誰でも戻せる
    • ハッシュ：改ざん検知とパスワード保存。同じ入力は同じ値、1文字変えると全く別の値
    • 暗号化：秘匿。鍵を持つ人だけが元に戻せる。鍵の管理が本体
    • エンコード（Base64 など）：表現の変換。秘密にならない。「Base64 で暗号化」は誤り
    • パスワードは SHA-256 ではなく bcrypt か Argon2id。速いハッシュは漏えいパスワードの辞書と照合されてしまう
  • 通信は全部 HTTPS：TLS 1.2 以上、証明書は Let's Encrypt かクラウドで自動更新、HSTS を付ける
    • 利用者との間だけでなく、サーバーと外部 API、サーバー同士も HTTPS
    • 証明書の検証を切らない：verify=False、rejectUnauthorized: false は本番で禁止
  • 保存の暗号化は「設定1つ」でできるが、アプリ経由の漏えいには効かない
    • ディスク・DB 全体の暗号化は、盗まれた機器やバックアップには効く
    • SQL インジェクションや認可の不備でアプリ経由に読まれるときは、復号済みの値が出ていく
    • 特に重要な列はフィールド単位で暗号化し、鍵はデータと別の場所（KMS）に置く
  • 暗号は自作しない。使ってよい部品は決まっている
    • 使う：AES-256-GCM、ChaCha20-Poly1305、SHA-256、HMAC-SHA256、Argon2id／bcrypt／scrypt、Ed25519／RSA 2048 ビット以上、TLS 1.2 以上
    • 使わない：MD5、SHA-1、DES／3DES、RC4、ECB モード、自作の暗号、ナンス（IV）の使い回し
  • 秘密情報の置き場所は4段階：コード ＜ 設定ファイル ＜ 環境変数 ＜ シークレット管理
    • .env は .gitignore に入れ、.env.example にはキー名だけ書く
    • CI のシークレット機能を使う。鍵は用途ごとに分け、最小権限にして、替える手順（ローテーション）を決めておく
    • ログに出さない
  • git に秘密を入れてしまったら、消す前に替える：① 無効化・ローテーション → ② 影響調査 → ③ 履歴から削除 → ④ 再発防止（gitleaks）
    • 公開リポジトリに入ったキーは数分でボットに拾われる。「消したから大丈夫」は通らない
  • 個人情報は「集めない・持たない・見せない」：必要な項目だけ、保持期間を決める、画面・ログ・CSV でマスキング、本番データを開発環境に持ち込まない
  • 乱数は暗号用のものを使う：secrets.token_urlsafe、crypto.randomBytes、crypto.randomUUID。Math.random と Python の random は予測できる

読み終えたら、本文を見ずに各項目を自分の言葉で説明できるか確かめてください。

1. ハッシュ・暗号化・エンコードの違い

この3つは、どれも「元の文字列を別の形にする」ので混同されますが、役割はまったく違います。違いは「元に戻せるか」と「戻すのに鍵が要るか」です。

方式元に戻せるか鍵用途例
ハッシュ
hash		戻せない（一方向）要らない改ざん検知（ファイルの同一性）、パスワードの保存SHA-256、bcrypt、Argon2
暗号化
encryption		鍵があれば戻せる要る秘匿。通信の中身、保存したデータAES-GCM、TLS
エンコード
encoding		誰でも戻せる要らない表現の変換。バイナリを文字にする、URL に入れるBase64、URL エンコード、16進数
署名
signature		（戻す目的ではない）秘密鍵で作り、公開鍵で確かめる本人が作ったことと、改ざんされていないことの確認Ed25519、RSA 署名、JWT の署名
⚠️間違えやすい点：「Base64 で暗号化」は暗号化ではない

Base64 は誰でも元に戻せる表現の変換です。トークンや設定ファイルの中身が Base64 で書かれていても、秘密は守られていません。「読めない文字列になっている」ことと「秘密である」ことは別です。

体験：SHA-256 を見る

🧪入力を1文字変えると、ハッシュはどう変わるか

2つの欄に文字列を入れると、それぞれの SHA-256 ハッシュ（256 ビットを16進数 64 文字で表示）が出ます。この計算はブラウザの中だけで行われ、どこにも送信されません。

入力 A
計算中…
入力 B
計算中…

ここで3つのことが分かります。同じ入力は必ず同じ値になる。1文字変えると全く別の値になる。値から元の入力は計算できない。この性質は改ざん検知には理想的です。しかしパスワードの保存には問題があります。「同じ入力は同じ値」なので、攻撃者は漏えいしたパスワードの辞書（数十億件）をあらかじめ SHA-256 にかけておけば、盗んだハッシュと照合するだけで元のパスワードが分かります。SHA-256 は1秒に数十億回計算できるため、辞書がなくても総当たりが現実的です。

✗ 危険な例：速いハッシュでパスワードを保存
Pythonimport hashlib

# 速いハッシュ。辞書と照合され、総当たりもできる
digest = hashlib.sha256(password.encode()).hexdigest()
db.execute("INSERT INTO users (email, pw) VALUES (?, ?)",
           (email, digest))
MD5・SHA-1・SHA-256 単体は「速い」ことが長所のハッシュです。パスワードには短所になります。ソルトを付けても、速さの問題は残ります。
✓ 安全な例：わざと遅いハッシュ（bcrypt）
Pythonimport bcrypt

# ソルト入りで、1回の計算に数十ミリ秒かかるよう設計されている
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt())
db.execute("INSERT INTO users (email, pw) VALUES (?, ?)",
           (email, hashed.decode()))

# 照合（保存した値にソルトが含まれているので、別に保存しなくてよい）
ok = bcrypt.checkpw(input_pw.encode(), stored.encode())
bcrypt・Argon2id・scrypt はソルトを自動で付け、わざと時間がかかる設計です。1件あたり数十ミリ秒なら利用者は気づきませんが、総当たりは数億倍遅くなります。Node なら argon2 や bcrypt パッケージ。パスワードの扱い全体は 第4章 2.。
🔑覚え方：「戻せない・鍵で戻せる・誰でも戻せる」

ハッシュは戻せない（改ざん検知・パスワード）。暗号化は鍵で戻せる（秘匿）。エンコードは誰でも戻せる（表現の変換）。パスワードだけは「戻せないハッシュ」の中でもわざと遅いものを選びます。

📰ニュースではこう報じられる：「パスワードはハッシュ化されていた」

流出の発表で「パスワードはハッシュ化されていたため、直ちに悪用される可能性は低い」と書かれることがあります。読み取るべき点はどのハッシュかです。bcrypt や Argon2 なら、強いパスワードはしばらく守られます。MD5・SHA-1・SHA-256 単体なら、よくあるパスワードは数時間で元に戻されると考えます。「ソルト付き」とあっても速いハッシュなら同じです。自分が利用者側なら、同じパスワードを使い回している他サービスも変えます。

2. 通信の暗号化：HTTPS／TLS

HTTP のままの通信は、同じ Wi-Fi にいる人や経路上の機器から盗聴（パスワードやセッション ID が丸見え）、改ざん（ページに別のスクリプトを差し込まれる）、なりすまし（偽サーバーに接続させられる）ができます。TLS はこの3つをまとめて防ぎます。

TLS が守る3つ：盗聴・改ざん・なりすまし
利用者ブラウザ
⇄TLS で暗号化
サーバー証明書で本物と証明
盗聴中身が読めない
改ざん書き換えると検知
なりすまし証明書で見破る
証明書は認証局が発行し、ブラウザが「このドメインの本物だ」と確かめる材料になります。無料の Let's Encrypt や、クラウドの証明書サービスで自動更新にするのが一般的です。
やること内容
全ページを HTTPS にログイン画面だけでなく全ページ。HTTP で来たアクセスは HTTPS へ転送（301）。多くはロードバランサーや CDN の設定1つ。
HSTS を付ける応答ヘッダー Strict-Transport-Security: max-age=31536000; includeSubDomains。ブラウザが「このサイトには今後 HTTPS でだけ接続する」と記憶し、最初の HTTP アクセスを狙う攻撃を防ぐ。
TLS 1.2 以上だけ許可TLS 1.0／1.1 と SSL は無効化する。クラウドやサーバーの推奨設定（Mozilla の設定ジェネレーターなど）に従う。
証明書の自動更新Let's Encrypt は 90 日で期限が切れる。 certbot やクラウドの証明書サービスで自動化し、期限切れの監視も入れる。
混在コンテンツをなくすHTTPS のページから HTTP の画像やスクリプトを読み込まない。ブラウザがブロックするか警告する。
サーバー間も HTTPS外部 API はもちろん、社内のサービス同士も HTTPS。「内部ネットワークだから平文」は、侵入された後に全部読まれる。
✗ 危険な例：証明書の検証を切る
Pythonimport requests

# 「証明書エラーが出たから」で検証を切ると、
# 偽サーバーに接続してもエラーにならない
r = requests.get(url, verify=False)
Node.js// 環境変数で全体の検証を無効化。最悪の形
process.env.NODE_TLS_REJECT_UNAUTHORIZED = "0";
// あるいは接続ごとに
https.get({ host, path, rejectUnauthorized: false }, cb);
検証を切ると、TLS の「なりすまし防止」が消えます。暗号化はされていても、相手が攻撃者の偽サーバーなら中身はすべて渡ります。開発中の一時しのぎが本番に残る事故が多い書き方です。
✓ 安全な例：検証は既定のまま。社内 CA なら証明書を渡す
Pythonimport requests

# 既定で検証する。何も書かないのが正解
r = requests.get(url)

# 社内の認証局で発行した証明書を使うサーバーなら、その CA 証明書を指定
r = requests.get(url, verify="/etc/ssl/certs/company-ca.pem")
Node.jsconst https = require("https"), fs = require("fs");
https.get({ host, path,
  ca: fs.readFileSync("/etc/ssl/certs/company-ca.pem") }, cb);
「証明書エラーが出る」の正しい直し方は、サーバー側の証明書を正しくするか、クライアントに正しい CA 証明書を渡すことです。検証を切る選択肢はありません。
🛠️実務ではこうする
  • 確かめ方：curl -I https://自分のサイト で Strict-Transport-Security があるか。curl -I http://自分のサイト が 301 で HTTPS に転送されるか。ブラウザの鍵アイコンから証明書の期限を見る。
  • レビューで言う一言：「verify=False と rejectUnauthorized: false は本番コードに1つもない？」をリポジトリ全体の検索で確かめる。
  • 期限切れの監視：証明書の期限が 14 日を切ったら通知する監視を1つ入れる。期限切れはサイト停止と同じ。

3. 保存の暗号化：できることと限界

通信の暗号化（移動中）に対して、ディスクや DB に書かれたデータの暗号化を保存時の暗号化といいます。クラウドのディスクやマネージド DB では設定1つで有効にでき、まずこれを入れます。ただし、何から守れて何から守れないかを知らないと「暗号化したから安全」という誤解につながります。

ディスク暗号化は「機器・バックアップの持ち出し」には効くが、「アプリ経由の読み出し」には効かない
攻撃者
→SQL インジェクション・認可の不備
アプリ正規の経路で復号済みの値を読む
→
DBアプリには平文で返す
→
ディスクここは暗号化
DB はアプリからの問い合わせに対して、復号した値を返すのが仕事です。アプリの穴から読まれるとき、ディスク暗号化は何もしません。守れるのは、ディスクやバックアップのファイルがそのまま持ち出された場合です。
段階守れるもの守れないものやること
ディスク・ボリューム全体機器の盗難、廃棄したディスク、スナップショットの持ち出しOS が動いている間の読み出し全部クラウドの設定で有効化。まず入れる
DB 全体（透過的暗号化）DB ファイルやバックアップの持ち出しDB に接続できる人・アプリからの読み出しマネージド DB の設定で有効化。バックアップも暗号化されるか確認
フィールド（列）単位DB に接続されても、鍵がなければ読めない。ログや CSV への流出も防ぎやすいアプリに鍵があるので、アプリ経由の読み出し特に重要な列（マイナンバー、口座、カード情報、医療情報）だけ。鍵は KMS に置き、データと別管理にする
💡イメージで理解する

ディスク暗号化は金庫ごと盗まれても開かないための鍵です。でも金庫の扉は、営業中は店員（アプリ）に対して開いています。店員になりすまして「出して」と言えば、中身は出てきます。だから、アプリの穴（第3・4章）をふさぐことと、本当に大事な物は金庫の中でさらに別の箱に入れる（フィールド単位の暗号化）ことが要ります。

⚠️間違えやすい点
  • 「DB は暗号化しているので SQL インジェクションが起きても大丈夫」→ 大丈夫ではありません。アプリ経由では復号済みの値が出ます。
  • フィールド単位の暗号化で、鍵を同じ DB の別テーブルやアプリのコードに置く → 一緒に持ち出されます。鍵は KMS か別のシークレット管理に。
  • バックアップだけ暗号化されていない → よくある抜け。バックアップの保存先の設定も確認します（第8章 4.）。

4. 自分で暗号を実装しない：使ってよい部品

暗号は自作しない、古いものを使わない、正しいモードで使うの3つを守ります。正しく実装された暗号ライブラリは各言語に標準で付いています。開発者がやるのは「どれを選ぶか」と「鍵とナンスを正しく扱うか」だけです。

目的✓ 使ってよい✗ 使わない
データの暗号化（共通鍵）AES-256-GCM、ChaCha20-Poly1305DES、3DES、RC4、Blowfish、AES の ECB モード、認証なしの CBC
ハッシュ（改ざん検知）SHA-256、SHA-384、SHA-3MD5、SHA-1
メッセージ認証HMAC-SHA256単純な SHA-256(秘密 + データ)（伸長攻撃の対象）
パスワードの保存Argon2id、bcrypt、scryptSHA-256 単体、MD5、ソルトなし
署名・鍵交換（公開鍵）Ed25519、ECDSA（P-256）、RSA 2048 ビット以上（できれば 3072）RSA 1024 ビット以下、DSA
通信TLS 1.2 以上（できれば 1.3）SSL 全般、TLS 1.0／1.1
ライブラリPython cryptography、Node crypto（標準）、Java javax.crypto、Go crypto/*、.NET System.Security.Cryptography自作、個人の実装、更新が止まったもの
✗ 危険な例：ECB モードとナンスの使い回し
Pythonfrom cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

# ECB：同じ平文ブロックが同じ暗号文になり、模様が残る。改ざんも検知できない
cipher = Cipher(algorithms.AES(key), modes.ECB())

# 固定のナンスを毎回使う。GCM では致命的（鍵が割れる）
nonce = b"000000000000"
ECB は「教科書の暗号」で、実用では使いません。GCM は正しく使えば強いですが、ナンスを同じ鍵で2回使うと安全性が崩れます。
✓ 安全な例：AES-256-GCM、ナンスは毎回新しく
Pythonimport os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)  # 鍵は KMS やシークレット管理に保管
aesgcm = AESGCM(key)

nonce = os.urandom(12)                     # 12 バイト。暗号化のたびに新しく作る
ct = aesgcm.encrypt(nonce, plaintext, None) # 認証タグ付き。改ざんすると復号で失敗する
stored = nonce + ct                         # ナンスは秘密ではないので一緒に保存してよい

# 復号
nonce, ct = stored[:12], stored[12:]
pt = aesgcm.decrypt(nonce, ct, None)
GCM は暗号化と改ざん検知を同時に行います（認証付き暗号）。守るのは鍵（外に出さない）とナンス（毎回新しく）の2つだけです。
🔑覚え方：「GCM・256・Argon2・Ed25519・TLS 1.2 以上」

共通鍵は AES-GCM、ハッシュは SHA-256、パスワードは Argon2id（または bcrypt）、署名は Ed25519、通信は TLS 1.2 以上。名前に「MD5」「SHA-1」「DES」「RC4」「ECB」が見えたら、それだけで要修正です。

5. 秘密情報の管理：置き場所の4段階

API キー、DB のパスワード、クラウドのアクセスキー、署名用の鍵、外部サービスのトークン。これらを秘密情報と呼びます。事故の多くは「置き場所」の問題です。置き場所には安全な順があります。

秘密情報の置き場所：右へ行くほど安全
コード履歴に永久に残る
→
設定ファイル誤コミットしやすい
→
環境変数リポジトリに入らない
→
シークレット管理暗号化・権限・履歴・自動更新
小さなプロジェクトは「環境変数（.env はコミットしない）」から。本番は AWS Secrets Manager、Google Cloud Secret Manager、Azure Key Vault、HashiCorp Vault などのシークレット管理へ。

STRIPE_KEY=        # Stripe ダッシュボード → 開発者 → API キー
DATABASE_URL=      # 1Password の「開発 DB」を参照
環境変数ならリポジトリに入りません。.env.example を置くと、新しいメンバーが「何を設定すればよいか」を値なしで知ることができます。
決めごと内容
CI のシークレットGitHub Actions なら ${{ secrets.NAME }}。ログにマスクされる。ワークフローのファイルに直接書かない。PR からの実行では渡さない設定にする（第7章 7.）。
用途ごとに分ける開発・検証・本番で別の鍵。サービスごとに別の鍵。1つ漏れても被害を限定でき、どれが漏れたか特定できる。
最小権限読み取りだけでよい処理に書き込み権限の鍵を渡さない。クラウドの鍵はロール（一時的な権限）で代替できないか先に考える（第7章 3.）。
ローテーション「替える手順」を先に作り、年1回は実際に替える。手順がないと、漏えい時に替えられず止まる。
ログに出さないリクエストやエラーをそのままログに書くと、ヘッダーの Authorization やクエリのトークンが残る。マスクしてから出す（第8章 2.）。
棚卸しどの鍵がどこで使われているかの一覧を持つ。退職者が作った鍵、使われていない鍵を消す（第8章 8.）。

6. git に秘密を入れてしまったら

誰でも一度はやります。大事なのは順番です。「消す」が最初ではありません。公開リポジトリに入ったクラウドのアクセスキーは、数分以内にボットが見つけて暗号通貨の採掘などに使い始めることが知られています。取られた前提で動きます。

STEP 1 ／ 今すぐ無効化してローテーション

そのキー・パスワード・トークンを発行元で無効化し、新しいものを作って差し替える。これが終わるまで、他のことはしない。

STEP 2 ／ 当日影響を調べる

いつからコミットされていたか。公開か非公開か。そのキーで何ができたか。クラウドなら利用履歴（CloudTrail など）に見覚えのない操作がないか。被害があれば第8章 5. の手順へ。

STEP 3 ／ 当日〜翌日履歴から削除

git filter-repo で該当ファイルを全履歴から除き、強制プッシュする。GitHub などは古いコミットがキャッシュに残ることがあるので、サポートに削除を依頼する。

STEP 4 ／ 今週再発防止

gitleaks を pre-commit と CI に入れる。GitHub の secret scanning と push protection を有効にする。.env が .gitignore にあるか確かめる。

シェル# 履歴から .env を完全に消す（git-filter-repo を事前にインストール。チームに周知してから）
git filter-repo --path .env --invert-paths
git push --force --all
git push --force --tags

# 再発防止：コミット前と CI でシークレットを検出する
gitleaks git .                         # リポジトリの履歴全体を検査
gitleaks protect --staged              # pre-commit フックで、ステージした変更だけ検査
⚠️間違えやすい点：「消したから大丈夫」
  • git revert や新しいコミットで削除しても、履歴には残ります。git log -p で誰でも見られます。
  • 履歴を書き換えても、すでにクローン・フォークした人の手元と、ホスティング側のキャッシュには残ります。だからローテーションが先です。
  • 「非公開リポジトリだから」も通りません。退職者のクローン、CI のログ、将来の公開への切り替えで出ます。
🛠️実務ではこうする：今日やる検索

リポジトリの全履歴を、AKIA（AWS アクセスキーの先頭）、sk_live・sk-、BEGIN PRIVATE KEY、password=、ghp_（GitHub トークン）で検索します。git log -p | grep -n "AKIA" でも、gitleaks を1回回しても構いません。見つかったら上の STEP 1 からです。

7. 個人情報とデータ最小化

個人情報は、持っているだけで漏えいのリスクと法律上の義務が発生します。守る技術より先に、そもそも持たないことが最も効く対策です。

原則やること例
集めないその機能に本当に必要な項目だけを入力させるニュースレター登録に生年月日や電話番号を求めない
持たない保持期間を決め、過ぎたら消す。カード番号は決済代行に任せ、自分の DB に保存しない退会後 30 日で個人情報を削除。注文履歴は匿名化して残す
見せない画面・ログ・CSV 出力・管理画面でマスキングする。必要な人にだけ、必要な範囲で090-****-1234、t***@example.com。サポート画面はカード番号の下4桁だけ
本番データを持ち出さない開発・検証環境に本番 DB のコピーを入れない。マスク済みデータか合成データを使う開発者の PC やテスト環境は本番より守りが弱い。そこから漏れる事故が多い
✗ 危険な例：ログに個人情報をそのまま出す
Pythonlogger.info(f"注文を受け付けました: {user.email} {user.phone} {card_number}")
ログ基盤は DB より多くの人が見られ、保管期間も長く、外部サービスに送られていることもあります。ログが第2の漏えい元になります。
✓ 安全な例：ID で追えるようにし、個人情報はマスク
Pythondef mask_email(e):
    name, _, domain = e.partition("@")
    return name[:1] + "***@" + domain

logger.info("注文を受け付けました",
            extra={"user_id": user.id, "order_id": order.id,
                   "email": mask_email(user.email)})
# カード番号はそもそもアプリに持たせない（決済代行のトークンを使う）
調査には利用者 ID と注文 ID があれば足ります。メールアドレスの本体は DB で引けます。
⚖️個人情報保護法との関係（概要）

個人情報を扱う事業者には、漏えい・滅失・毀損を防ぐ安全管理措置（アクセス制御、暗号化、ログ、委託先の監督など）が義務づけられています。一定の漏えい（要配慮個人情報、財産的被害のおそれ、不正アクセスによるもの、1,000 人超など）は個人情報保護委員会への報告と本人への通知が必要です。細かい要件は法務・専門家と確認してください。開発者として覚えるのは「持たなければ義務も減る」「漏えいしたら報告の期限がある」の2点です（報告の流れは第8章 7.）。

8. 乱数：トークンに使ってよい乱数

セッション ID、パスワードリセットのトークン、API キー、招待コード。これらは「推測できない」ことが安全性のすべてです。ところが、多くの言語の標準の乱数（Math.random、Python の random）は統計的にはランダムでも、暗号的には予測可能です。いくつかの出力を観察すると、次の値が計算できます。

✗ 危険な例：一般用の乱数でトークンを作る
JavaScript// 観測した値から次の値が予測できる
const token = Math.random().toString(36).slice(2);
Pythonimport random, string
# random はシミュレーション用。暗号用ではない
token = "".join(random.choice(string.ascii_letters) for _ in range(8))
予測できるトークンは、他人のパスワードリセットを乗っ取る、他人のセッションを推測する、といった事故に直結します。8文字では短すぎる点も問題です。
✓ 安全な例：暗号用の乱数、128 ビット以上
JavaScriptconst crypto = require("crypto");
const token = crypto.randomBytes(32).toString("base64url"); // 256 ビット
const id = crypto.randomUUID();                             // 122 ビットの乱数を含む UUID v4
Pythonimport secrets
token = secrets.token_urlsafe(32)   # 32 バイト＝256 ビット。URL に入れられる文字だけ
code = secrets.randbelow(10**6)      # 0〜999999 の数値コード（有効期限と試行回数の制限も付ける）
「crypto」「secrets」と名前に付いたものを使います。長さは 128 ビット（16 バイト）以上。ブラウザでは crypto.getRandomValues。
🔑覚え方：「secrets か crypto の付いた乱数、16 バイト以上」

Python は secrets、Node は crypto、ブラウザは crypto.getRandomValues。random と Math.random は、ゲームの演出やテストデータにだけ使います。

📝用語の補足
ソルト
パスワードごとに付ける乱数。同じパスワードでも違うハッシュ値になり、辞書との一括照合を防ぐ。bcrypt・Argon2 は自動で付ける。
ナンス（IV）
暗号化のたびに変える使い捨ての値。同じ鍵で同じナンスを2回使うと GCM の安全性が崩れる。秘密ではないので暗号文と一緒に保存してよい。
認証付き暗号
暗号化と改ざん検知を同時に行う方式。AES-GCM、ChaCha20-Poly1305。改ざんされた暗号文は復号時に失敗する。
認証局（CA）
サイトの運営者を確認して TLS 証明書を発行する機関。Let's Encrypt は無料で自動化できる。
HSTS
「このサイトには今後 HTTPS でだけ接続せよ」とブラウザに記憶させる応答ヘッダー。
KMS
鍵を安全に作り・保管し・使うためのサービス。鍵そのものはサービスの外に出ない。
シークレット管理
秘密情報を暗号化して保管し、権限を付けてアプリに配るサービス。AWS Secrets Manager、Vault など。
ローテーション
鍵やパスワードを新しいものに替え、古いものを無効化すること。
マスキング
個人情報の一部を伏せ字にして表示・記録すること。090-****-1234 など。
データ最小化
目的に必要な最小限の個人情報だけを集め、必要な期間だけ持つという原則。

🧠 想起練習

本文を見ずに答えを思い出してから、各項目を開いて確認してください。

ハッシュ・暗号化・エンコードの違いを「戻せるか」で説明してください。
ハッシュ＝戻せない（改ざん検知・パスワード）。暗号化＝鍵があれば戻せる（秘匿）。エンコード＝誰でも戻せる（Base64 などの表現の変換。秘密にならない）。
パスワードの保存に SHA-256 単体が不適切な理由と、代わりに使うものは？
速いので、漏えいパスワードの辞書と照合されたり総当たりされたりする。代わりに bcrypt・Argon2id・scrypt（ソルト自動、わざと遅い）。
TLS が防ぐ3つは？
盗聴（中身が読めない）、改ざん（書き換えると検知）、なりすまし（証明書で見破る）。
verify=False／rejectUnauthorized: false を本番で使ってはいけない理由と、正しい直し方は？
なりすまし防止が消え、偽サーバーに中身を渡してしまう。正しくは、サーバーの証明書を直すか、クライアントに正しい CA 証明書を渡す。
HSTS とは？ヘッダーの例は？
「今後このサイトには HTTPS でだけ接続せよ」とブラウザに記憶させる仕組み。Strict-Transport-Security: max-age=31536000; includeSubDomains。
ディスク・DB 全体の暗号化で守れるものと守れないものは？
守れる＝機器やバックアップの持ち出し。守れない＝SQL インジェクションや認可の不備などアプリ経由の読み出し（復号済みの値が返る）。重要な列はフィールド単位で暗号化し、鍵は KMS に。
使ってよい暗号部品を目的別に5つ挙げてください。
共通鍵＝AES-256-GCM、ハッシュ＝SHA-256、パスワード＝Argon2id／bcrypt、署名＝Ed25519（または RSA 2048 以上）、通信＝TLS 1.2 以上。
AES-GCM を使うときに守る2つのことは？
鍵を外に出さない（KMS・シークレット管理に置く）。ナンスは暗号化のたびに新しく作る（同じ鍵で使い回さない）。
秘密情報の置き場所の4段階を安全な順に。
コード ＜ 設定ファイル ＜ 環境変数 ＜ シークレット管理（AWS Secrets Manager、Vault など）。
git に API キーを入れてしまったときの手順4つを順に。
① 無効化してローテーション → ② 影響調査（いつから、公開か、利用履歴）→ ③ 履歴から削除（git filter-repo、ホスティングのキャッシュ削除依頼）→ ④ 再発防止（gitleaks、secret scanning、.gitignore）。
個人情報を守る「3つのない」と、本番データについての約束は？
集めない・持たない・見せない。本番データを開発・検証環境にコピーしない（マスク済みか合成データを使う）。
トークンや ID に使ってよい乱数と、だめな乱数は？長さの目安は？
よい＝secrets.token_urlsafe、crypto.randomBytes、crypto.randomUUID、crypto.getRandomValues。だめ＝Math.random、Python の random。128 ビット（16 バイト）以上。
