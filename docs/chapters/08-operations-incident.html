第8章 運用：ログ・監視・バックアップ・インシデント対応

作って終わりではありません。攻撃は運用中に来ます。予防をどれだけ固めても穴はゼロにならないので、起きたことに気づく（ログ・監視）、壊れても戻せる（バックアップ）、起きたときに迷わず動ける（手順）の3つを用意しておきます。この章は、個人開発でも小さなチームでも、そのまま使える最低限の形を示します。

🧭この章で理解してほしいこと
  • 運用の仕事は検知・回復・対応の3つ：予防だけでは足りない（OWASP Top 10:2025 A09「セキュリティログとアラートの不備」）
    • 検知：ログを残し、兆候にアラートを付ける。回復：バックアップから戻せる。対応：手順書どおりに動く
  • ログに残すもの・残さないもの
    • 残す：認証の成功・失敗、権限の変更、重要データの参照・変更・削除・エクスポート、管理操作、入力検証エラー、例外。「誰が・いつ・何に・何を・結果」の形で
    • 残さない：パスワード、トークン・セッション ID、カード番号、個人情報の本体。出力前にマスクする
    • 形式：構造化（JSON）、時刻は UTC かタイムゾーン明記、リクエストを追う相関 ID
    • 保管：1か所に集め、追記のみ・別の権限で守る（侵入者はログを消しに来る）。保管期間は規程で決める
  • 監視の兆候は7つ：ログイン失敗の急増、深夜の管理操作、権限の変更、大量エクスポート、外向きの異常通信、CPU の急騰、新しい管理者アカウント
    • アラートは少数の確実な条件から始める。鳴りすぎると見なくなる（アラート疲れ）
  • バックアップは 3-2-1、書き換え不可、復元テスト：ランサム攻撃は IPA 10大脅威 2026 の1位
    • 3つの複製、2種類の媒体、1つは別の場所。1つは書き換え不可（イミュータブル）かオフライン
    • ランサムウェアはバックアップから消しに来る。本番とは別の権限・別アカウントで守る
    • 取っているだけでは意味がない。戻せることを定期的に試す。RPO（失ってよい期間）と RTO（戻すまでの時間）を決める
  • インシデント対応は6段階：検知 → 初動 → 封じ込め → 根絶 → 復旧 → 振り返り
    • 初動は「記録・連絡・証拠保全」。慌てて消さない、再起動しない
    • 封じ込めは認証情報のローテーションと該当サーバーの隔離。連絡先と手順を1枚にして全員が場所を知る
    • 困ったら JPCERT/CC に相談できる
  • 脆弱性情報は受け取る仕組みを作り、3問で仕分けする
    • 情報源：GitHub の Dependabot alerts、JVN、IPA、使っている製品のセキュリティアドバイザリ
    • 手順：影響判断（使っているか・届くか・直したか）→ 一時対策 → パッチ → 確認 → 記録
    • 期限の例：Critical は当日、High は1週間以内、Medium は次の定期リリース
  • 個人情報が漏えいしたら法律上の報告義務がある：個人情報保護委員会への報告と本人への通知。速報はおおむね3〜5日以内、確報は30日以内（不正目的なら60日以内）。詳細は法務・専門家へ
  • 権限の棚卸しは定期作業：退職・異動の当日にアカウント削除、不要な API キーの削除、共有アカウントの廃止、鍵のローテーション、年1回の見直し

読み終えたら、本文を見ずに各項目を自分の言葉で説明できるか確かめてください。

1. 運用で守ること：検知・回復・対応

第1章で、対策には予防・検知・回復の3種類があると整理しました。第3〜7章はほぼ予防の話です。この章は残りの2つと、実際に起きたときの「対応」を扱います。

予防をすり抜けた攻撃に、検知と回復で備える
予防第3〜7章
→すり抜け
検知ログ・監視（2〜3節）
→気づいたら
対応手順書（5〜7節）
→戻す
回復バックアップ（4節）
OWASP Top 10:2025 の A09「セキュリティログとアラートの不備」は、攻撃されても気づけない状態そのものを脆弱性として数えています。
💡イメージで理解する

家の防犯で言えば、鍵（予防）に加えて、防犯カメラと通知（検知）、火災保険と貴重品の別保管（回復）、避難経路と緊急連絡先の紙（対応）です。鍵だけ頑丈にしても、入られたことに1か月気づかなければ被害は広がります。

2. ログ：何を残し、何を残さないか

ログは「後から何が起きたかを再現する」唯一の材料です。しかし、何でも出せばよいわけではありません。ログに秘密を書くと、ログ基盤が第2の漏えい元になります。

残す（誰が・いつ・何に・何を・結果）残さない（出力前にマスク）
ログインの成功・失敗（利用者 ID、送信元 IP、結果）パスワード（失敗時の入力値も）
権限・ロールの変更、管理者アカウントの作成セッション ID、API トークン、Authorization ヘッダー、Cookie
重要データの参照・変更・削除・エクスポートクレジットカード番号、口座番号
管理画面の操作、設定変更、デプロイ個人情報の本体（氏名・住所・メール本文）。ID で参照できれば十分
入力検証のエラー（攻撃の試行の兆候）、例外・スタックトレース（ログにだけ）リクエストボディ・レスポンスボディの丸ごと
✗ 危険な例：リクエストを丸ごと出す
Python（Flask）@app.post("/login")
def login():
    body = request.get_json()
    app.logger.info(f"login request: {body}")
    # → {"email": "...", "password": "hunter2"} がログに残る
    ...
パスワードがログ基盤・バックアップ・監視ツールの画面に残り、閲覧できる人全員に見える。
✓ 安全な例：項目を選び、秘密はマスクする
Python（Flask）import logging, json
SECRET_KEYS = {"password", "token",
               "authorization", "card_number"}

class MaskFilter(logging.Filter):
    def filter(self, record):
        if isinstance(record.msg, dict):
            record.msg = {
                k: ("***" if k.lower() in SECRET_KEYS
                    else v)
                for k, v in record.msg.items()
            }
        return True
app.logger.addFilter(MaskFilter())

@app.post("/login")
def login():
    ...
    app.logger.info({
        "event": "login", "user_id": user.id,
        "ip": request.remote_addr, "result": "ok",
        "request_id": g.request_id,
    })
出す項目を決めて構造化し、万一秘密のキーが混ざってもフィルタで伏せる。
観点決めること
形式構造化ログ（JSON）。項目名を統一する（event、user_id、ip、result、request_id）
時刻UTC に統一するか、タイムゾーンを明記する（2026-10-22T03:14:15Z）。サーバー間で時刻を同期する（NTP）。ずれていると事故の時系列が組めない
追跡リクエストごとに相関 IDを発行し、全ログに付ける。利用者に見せるエラーの「問い合わせ番号」にも使える
保管1か所に集める（ログ基盤・クラウドのログサービス）。追記のみ・削除不可にし、本番サーバーの権限では消せないようにする。侵入者は痕跡を消しに来る
期間規程で決める（例：認証・操作ログは1年、アクセスログは90日）。侵入から発覚まで数か月かかることがあるので短すぎない期間にする
🛠️実務ではこうする：ログの確かめ方
  • わざとログインに失敗し、ログに「誰が・いつ・どこから・失敗」が残り、入力したパスワードが残っていないことを見る。
  • ログ全体を password・token・Authorization・Bearer で検索し、値が入っていないか確かめる。
  • 本番サーバーにログインしたままログ基盤のログを削除できるか試す。できたら権限の分離が足りない。

3. 監視とアラート：異常の兆候

ログを集めただけでは、誰も見ません。少数の確実な兆候にアラートを付け、通知が来たら必ず見る、という状態を作ります。最初から条件を増やすと、鳴りすぎて誰も見なくなります（アラート疲れ）。

兆候疑うことアラート条件の例
ログイン失敗の急増総当たり、パスワードリスト攻撃（第4章）同じ IP から1分に10回以上の失敗。同じ利用者に対して多数の IP から失敗
深夜・休日の管理操作乗っ取られたアカウントによる操作業務時間外の管理画面ログイン、設定変更
権限の変更・新しい管理者権限昇格、侵入者による足場づくり管理者ロールの付与、新規管理者アカウント作成は毎回通知
大量のデータ参照・エクスポート情報の持ち出し（外部・内部）1利用者あたりの参照件数が普段の10倍、エクスポート機能の連続実行
外向きの異常な通信侵入後の持ち出し、攻撃者のサーバーへの接続サーバーから見覚えのない宛先への通信、送信量の急増
CPU・費用の急騰暗号資産マイニング、乗っ取られたクラウドアカウントでのサーバー大量起動CPU が長時間 100%、クラウドの請求アラート（予算の超過）
入力検証エラー・4xx の急増脆弱性の探索（スキャン）特定の経路への 400／403／404 が短時間に集中
🔑覚え方：最初の3つは「失敗・権限・外向き」

全部をいきなり入れる必要はありません。ログイン失敗の急増、権限の変更、外向きの異常通信（または請求アラート）の3つから始めれば、侵入の「入口・足場・持ち出し」の3段階それぞれに1つずつ目が付きます。

🛠️実務ではこうする
  • アラートは必ず人に届く経路（チャット・メール・電話）に送る。ダッシュボードに出るだけでは誰も見ない。
  • 作ったらわざと鳴らす（テスト用アカウントで10回ログイン失敗する）。鳴らないアラートは無いのと同じ。
  • 鳴ったときに「何を見て、誰に連絡するか」を5節の手順書に書いておく。

4. バックアップとランサムウェア

ランサム攻撃は IPA 10大脅威 2026 の組織向け1位で、11年連続の選出です。侵入後にデータを暗号化して業務を止め、復旧と「公開しない」ことの両方に金銭を要求します。攻撃者は暗号化の前にバックアップを探して消すので、「毎晩取っている」だけでは守れません。

📰ニュースではこう報じられる

「ランサムウェア被害により基幹システムが停止し、受注・出荷を停止。バックアップも暗号化されており、復旧のめどは立っていない。」

  • 「基幹システムが停止」→ 壊れたのは可用性（第1章）。売上に直結するので金銭要求が通りやすい
  • 「バックアップも暗号化」→ バックアップが本番と同じネットワーク・同じ権限で書き換え可能だった
  • 「復旧のめどが立たない」→ 復元の手順と所要時間（RTO）を事前に試していなかった
3-2-1 ルール：3つの複製、2種類の媒体、1つは別の場所（うち1つは書き換え不可）
本番データ1つ目
→
同じ拠点の別媒体2つ目：すばやく戻す用
→
別の場所・別権限3つ目：書き換え不可
3つ目は本番の権限では書き込みも削除もできないようにする。クラウドならバージョニング＋オブジェクトロック、または別アカウント。物理ならネットワークから切り離したオフライン媒体。
観点決めること・やること
RPO
Recovery Point Objective		失ってよいデータの期間。「1日分なら許容」なら毎日、「1時間」なら継続的なレプリケーションやログ出荷が要る
RTO
Recovery Time Objective		戻すまでに許される時間。「4時間」なら、復元手順を4時間以内でできることを実際に試して確かめる
書き換え不可イミュータブル（オブジェクトロック）か、オフライン媒体。本番の認証情報では触れない権限にする
暗号化とアクセス制御バックアップには全データが入る。保存時に暗号化し、読める人を最小にする（第5章）。公開バケットに置くのは論外（第7章）
復元テスト四半期に1回など、実際にバックアップから別環境へ復元して起動する。手順書に所要時間を記録する
範囲DB だけでなく、設定（IaC）、秘密情報（別経路で）、アップロードされたファイル、鍵。「DB は戻ったがファイルが無い」を防ぐ
✗ 危険な例：同じサーバーに、同じ権限で
crontab# 毎晩3時に、同じサーバーの別フォルダへ
0 3 * * * pg_dump mydb > /var/backups/mydb.sql
# 本番と同じディスク、同じ root 権限、暗号化なし
# 復元は一度も試していない
サーバーが暗号化されればバックアップも一緒に暗号化される。侵入者は rm 一発で消せる。
✓ 安全な例：別の場所へ、書き込み専用の権限で、暗号化して
crontab（概要）# 書き込み専用のロールで、別アカウントのバケットへ
0 3 * * * pg_dump mydb | gzip \
  | gpg -e -r backup@example.com \
  | aws s3 cp - s3://backup-bucket/mydb/$(date +\%F).sql.gz.gpg
# バケット側：バージョニング ON、オブジェクトロック（例：35日）、
# 本番ロールには put だけ許可し、delete と list は不許可
# 四半期ごとに別環境へ復元して起動することを試す
本番の権限では消せない。暗号化されているので置き場所が漏れても読めない。復元できることを試している。
⚠️間違えやすい点
  • 「クラウドの DB だから自動バックアップがある」→ 自動バックアップは同じアカウント・同じ権限で消せることが多い。アカウント乗っ取りには効かない。別アカウントへのコピーを足す。
  • 「レプリカ（複製）があるからバックアップ不要」→ レプリカは誤削除・暗号化も即座に複製する。バックアップとは別物。
  • 「身代金を払えば戻る」→ 戻る保証はなく、支払いが次の攻撃の資金になる。払わなくて済むようにバックアップを守る。

5. インシデント対応の手順

事故は「起きるか」ではなく「いつ起きるか」です。起きてから考えると、慌てて証拠を消し、連絡が遅れ、被害が広がります。手順を1枚にまとめ、全員がその場所を知っている状態にしておきます。個人開発でも、自分用に書いておく価値があります。

インシデント対応の6段階
① 検知
→
② 初動記録・連絡・保全
→
③ 封じ込め隔離・鍵の交換
→
④ 根絶原因を直す
→
⑤ 復旧
→
⑥ 振り返り
段階やることやってはいけないこと
① 検知アラート、利用者からの連絡、外部からの指摘、ログの異常。「おかしい」と思ったら手順を開く「気のせい」で済ませる。1人で抱える
② 初動記録（時刻・見たもの・やったことを時系列でメモ）、連絡（責任者・チーム。決めてある連絡先へ）、証拠保全（ログのコピー、ディスクやメモリのスナップショット、時刻の確認）慌てて消す・再起動する。メモリ上の証拠とログが消える。攻撃者に気づいたことを知らせる操作も避ける
③ 封じ込め該当サーバーをネットワークから隔離（止めずに切り離す）、漏れた可能性のある認証情報をすべてローテーション（パスワード・API キー・セッションの無効化）、不正なアカウントの停止原因が分からないまま「とりあえず戻す」。同じ穴から再侵入される
④ 根絶侵入経路を特定して直す（パッチ・設定・コード）。仕込まれたもの（バックドア・不正アカウント・改ざんファイル）を取り除く。必要なら作り直す見つかったマルウェアだけ消して終わる
⑤ 復旧きれいな状態（バックアップ・再構築）から戻す。監視を強化した状態で段階的に再開する侵害された可能性のある状態のまま再開する
⑥ 振り返り時系列をまとめ、「なぜ防げなかったか」「なぜ気づくのに時間がかかったか」を個人を責めずに分析し、対策を期限付きで決める犯人探しで終わる。報告書を書いて読まれない
🔑覚え方：初動は「消すな・切るな・書き残せ」

再起動しない（消すな）、電源を切らない（切るな）、時刻と行動をメモする（書き残せ）。ネットワークから切り離すのは可。これだけ守れば、後から専門家が調査できます。

手順書は、次のような1枚で十分です。リポジトリの docs/ や Wiki など、本番が止まっていても読める場所に置きます。

docs/incident-response.md（例）# インシデント対応 1枚シート

## 連絡先（この順に）
1. 責任者：〇〇（電話・チャット）
2. インフラ担当：〇〇
3. 法務・広報（個人情報の漏えいの可能性があるとき）：〇〇

## 初動チェック
- [ ] 時刻・見たもの・やったことを時系列でメモし始めた
- [ ] 責任者に連絡した（1人で抱えない）
- [ ] 再起動・電源断・ファイル削除をしていない
- [ ] ログをコピーし、スナップショットを取った
- [ ] 該当サーバーをネットワークから隔離した
- [ ] 漏れた可能性のある認証情報をローテーションした

## 判断
- 個人情報が含まれる可能性 → 7節の報告義務を確認。法務へ
- カード情報が含まれる可能性 → 決済代行・カード会社の手続きへ

## 復旧後
- [ ] 振り返り（責めない）を1週間以内に実施
- [ ] 対策に期限と担当を付けた
🔬相談先

JPCERT/CC はインシデントの報告・相談を受け付けている日本の組織です。また、各都道府県警察にはサイバー犯罪の相談窓口があります。攻撃者と単独で交渉せず、専門家と法務に相談してください。

6. 脆弱性情報の追い方と対応手順

脆弱性は毎日公表されます。全部を読む必要はありません。自分が使っている部品の情報だけが届く仕組みを作り、届いたら第1章の3問で仕分けします。

情報源何が届くか設定

7. 個人情報漏えい時の報告義務

⚖️個人情報が漏えいしたら、報告と通知が法律上の義務

個人情報保護法では、一定の漏えい等が起きた（おそれがある）場合、事業者は個人情報保護委員会への報告と本人への通知が義務です。おおむね次の場合が対象です。

  • 要配慮個人情報（病歴・信条など）の漏えい
  • 財産的被害が生じるおそれがある漏えい（クレジットカード番号・口座情報など）
  • 不正の目的による漏えい（不正アクセス、ランサムウェアなど）
  • 1,000 人を超える漏えい

報告は2段階で、速報はおおむね3〜5日以内、確報は30日以内（不正の目的によるものは60日以内）とされています。「漏えいしたおそれ」の段階で対象になるので、公開状態になっていた期間は「取られた前提」で判断します。日数や対象は法改正で変わることがあるため、必ず個人情報保護委員会の最新の案内を確認し、判断は法務・専門家と一緒に行ってください。

クレジットカード情報が関わる場合は、別途、決済代行会社・カード会社への連絡と、加盟店契約・PCI DSS に基づく手続きが必要です。

開発者が知っておくべきことは3つです。① 漏えいの可能性に気づいたら、自分で判断を抱えずすぐに責任者へ上げる（初動の「連絡」）。② 何件・どの項目が漏れた可能性があるかを答えられるのは開発者なので、ログとデータの構造から特定する準備をしておく。③ 期限が短いので、5節の手順書に「個人情報の可能性 → 法務へ」の一行を入れておく。

8. 権限の棚卸し

権限とアカウントは、放っておくと増える一方です。退職者のアカウント、作ったまま忘れた API キー、全員が知っている共有パスワード。これらは内部不正（IPA 10大脅威 2026 の7位）と、乗っ取り後の横移動の両方に使われます。

いつやること
退職・異動の当日アカウントの無効化、SSO からの削除、その人が知っていた共有パスワード・鍵のローテーション。「当日」が守れるよう、入退社手続きに組み込む
月1回管理者権限を持つアカウントの一覧を見て、全員に理由があるか確認する。新しい管理者が増えていないか
四半期に1回API キー・アクセスキーの一覧と最終使用日を見て、使っていないものを削除する。90日以上更新していないキーをローテーションする
年1回チェックリストの「運用のとき」を全部見直す。公開範囲（第7章）、ログの保管期間、バックアップの復元テスト、手順書の連絡先
常に共有アカウントを作らない（誰の操作か分からなくなる）。やむを得ない場合はパスワードマネージャーで管理し、操作ログで追えるようにする
🛠️実務ではこうする：運用で言う一言
  • 「このログ、トークンがそのまま出ていませんか？ 保管期間と削除権限はどうなっていますか？」
  • 「ログイン失敗の急増と管理者の追加、アラートは鳴りますか？ 最後に鳴らしたのはいつですか？」
  • 「バックアップ、本番の権限で消せますか？ 最後に復元を試したのはいつですか？」
  • 「事故が起きたら、最初に誰に連絡しますか？ 手順書はどこにありますか？」
  • 「先月退職した人のアカウントと、その人が知っていた鍵はどうなっていますか？」
⚠️間違えやすい点
  • 「ログは全部残しておけば安心」→ 秘密を含むログは第2の漏えい元。何を残さないかを先に決める。
  • 「監視ツールを入れたから見えている」→ 人に届くアラートがなければ誰も見ない。わざと鳴らして確かめる。
  • 「不審だったのでサーバーを再起動して直った」→ 証拠が消え、侵入経路も残ったまま。再起動の前に記録と保全。
  • 「漏えいしたか確証がないので報告はまだ」→ 「おそれ」の段階で義務が生じる。法務と相談して判断する。

📝用語の補足
構造化ログ
JSON などの決まった形式で項目ごとに残すログ。検索・集計・アラートがしやすい。
相関 ID
1つのリクエストに付ける一意の ID。複数のサービスをまたいでログをつなげる。利用者に見せる問い合わせ番号にも使える。
NTP
サーバーの時刻を合わせる仕組み。ずれていると事故の時系列が組めない。
アラート疲れ
通知が多すぎて重要なものまで無視されるようになる状態。少数の確実な条件から始める。
3-2-1 ルール
バックアップは3つの複製、2種類の媒体、1つは別の場所に置く、という目安。
イミュータブル
一度書いたら期間内は変更も削除もできない保存方式。オブジェクトロックなど。
RPO／RTO
RPO は失ってよいデータの期間、RTO は戻すまでに許される時間。バックアップの頻度と復元手順を決める基準。
封じ込め
被害がこれ以上広がらないようにする処置。隔離と認証情報のローテーション。
証拠保全
調査に必要なログ・ディスク・メモリの状態を、消えたり変わったりする前に保存すること。
バックドア
侵入者が再び入るために仕込む裏口。不正アカウント・改ざんされたプログラムなど。
要配慮個人情報
人種・信条・病歴・犯罪歴など、特に慎重な扱いが必要と法律で定められた個人情報。

🧠 想起練習

本文を見ずに答えを思い出してから、各項目を開いて確認してください。

運用の仕事3つと、それぞれの手段は？
検知（ログ・監視・アラート）、回復（バックアップ）、対応（手順書どおりに動く）。予防だけでは足りない（OWASP A09）。
ログに残すものを5つ、残さないものを4つ挙げてください。
残す：認証の成否、権限の変更、重要データの参照・変更・削除・エクスポート、管理操作、入力検証エラー・例外。残さない：パスワード、トークン・セッション ID、カード番号、個人情報の本体。
ログの形式・時刻・追跡・保管で決めることは？
JSON の構造化ログ／UTC かタイムゾーン明記、NTP で同期／相関 ID を全ログに／1か所に集め、追記のみ・本番の権限では消せないようにし、保管期間を規程で決める。
監視の兆候を5つ以上挙げてください。最初に入れる3つは？
ログイン失敗の急増、深夜の管理操作、権限の変更・新しい管理者、大量エクスポート、外向きの異常通信、CPU・費用の急騰、4xx の急増。最初は「失敗・権限・外向き（または請求アラート）」。
アラートを作った後に必ずすることは？
わざと鳴らして、人に届く経路（チャット・メール・電話）に通知が来ることを確かめる。鳴ったときの行動を手順書に書く。
3-2-1 ルールとは？ランサムウェアに効くために足す条件は？
3つの複製、2種類の媒体、1つは別の場所。うち1つは書き換え不可（オブジェクトロック）かオフラインにし、本番の権限では消せないようにする。
「同じサーバーの別フォルダに毎晩バックアップ」はなぜ効かないか。
サーバーが暗号化されれば一緒に暗号化され、侵入者に一発で消される。別の場所・別権限・暗号化・復元テストが要る。
RPO と RTO とは？
RPO＝失ってよいデータの期間（バックアップの頻度を決める）。RTO＝戻すまでに許される時間（復元手順を実際に試して確かめる）。
インシデント対応の6段階を順に言ってください。
検知 → 初動（記録・連絡・証拠保全）→ 封じ込め（隔離・認証情報のローテーション）→ 根絶（原因を直す）→ 復旧（きれいな状態から）→ 振り返り（責めない）。
不審なログインを見つけたとき、再起動してよいですか。初動の合言葉は？
だめ。メモリ上の証拠とログが消える。「消すな・切るな・書き残せ」。ネットワークからの隔離は可。
脆弱性情報の対応手順5段階と、Critical・High・Medium の期限の例は？
影響判断（3問）→ 一時対策 → パッチ適用 → 確認 → 記録。Critical は当日、High は1週間以内、Medium は次の定期リリース。
個人情報が漏えいしたときの法律上の義務と、報告の期限の目安は？
個人情報保護委員会への報告と本人への通知。速報はおおむね3〜5日以内、確報は30日以内（不正目的なら60日以内）。「おそれ」の段階で対象。判断は法務・専門家と。
