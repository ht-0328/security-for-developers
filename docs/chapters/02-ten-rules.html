基礎実装

第2章 まずこれだけ：開発者が守る10のルール

細かい攻撃名を知らなくても、この10個を守れば「よくある穴」の大半はふさがります。各ルールは「何を・なぜ（どんな事故になるか）・どうやって・どう確かめるか」の4点で書いています。詳しい原理は第3章以降で扱うので、ここでは行動を決めることが目的です。

🧭この章で理解してほしいこと
  • 入口を固める（ルール 1〜4）
    1. 外から来るものは全部疑う：入力の検証はサーバー側で、型・長さ・範囲・許可リスト
    2. 文字列をつなげて命令を作らない：SQL はプレースホルダ、HTML はテンプレートの自動エスケープ、OS コマンドは呼ばない
    3. 認証は自分で作らない：フレームワーク標準か認証サービス。パスワードは bcrypt／Argon2、多要素認証を用意
    4. 「何をしてよいか」は毎回サーバーで確かめる：URL の ID を変えても他人のものが見えない。許可されていなければ拒否
  • 宝を隠す（ルール 5〜6）
    1. 秘密はコードに書かない：環境変数かシークレット管理。漏れたら即ローテーション
    2. 通信は全部 HTTPS、Cookie には Secure・HttpOnly・SameSite
  • 家を整える（ルール 7〜8）
    1. 部品は最新に保つ：lock ファイル、自動更新、スキャン、EoL を使わない
    2. 必要最小限だけ開ける：ポート・公開設定・権限・管理画面は「閉」が初期値
  • 見張る（ルール 9〜10）
    1. 記録は残す、秘密は残さない：誰が何をしたかをログに、パスワードやカード番号はログに書かない。利用者には一般的なエラー文
    2. 人の目と機械の目に乗せる：PR テンプレートにチェック項目、CI に自動検査、設計時に「悪用されたら」を1回
  • 明日からの3手：今日 依存スキャンを1回回す／今週 秘密情報がリポジトリにないか検索する／今月 チェックリストを PR テンプレートに入れる

読み終えたら、本文を見ずに10個を自分の言葉で言えるか確かめてください。

読む前の問い（答えを予測してから読み進め、読み終えたら答え合わせをしてください）

  • 画面側（JavaScript）で入力チェックをしていれば、サーバー側のチェックは省いてよいか。
  • API キーを config.js に書いて、リポジトリは非公開にしてある。問題はあるか。
  • 「社内の人しか使わないシステム」に、認可の確認は要るか。

1. 10のルールの一覧と、4つのまとまり

10のルールは「入口を固める・宝を隠す・家を整える・見張る」の4つに分かれる
入口を固める
1 疑う
2 つながない
3 作らない
4 確かめる
宝を隠す
5 書かない
6 暗号化
家を整える
7 最新に
8 閉じる
見張る
9 残す
10 乗せる
🔑覚え方：「疑う・つながない・作らない・確かめる／書かない・暗号化／最新に・閉じる／残す・乗せる」

4つのまとまりで思い出します。入口（入ってくるものを疑い、命令につなげず、認証は作らず、権限を確かめる）→ 宝（秘密を書かず、通信を暗号化）→ 家（部品を最新に、不要な扉は閉じる）→ 見張り（記録を残し、レビューと検査に乗せる）。

2. 入口を固める：ルール 1〜4

RULE 1
外から来るものは全部疑う（入力はサーバー側で検証する）
何を
フォームの値、URL のパラメータ、HTTP ヘッダー、Cookie、アップロードされたファイル、外部 API の応答。利用者のブラウザから来るものは、すべて攻撃者が自由に書き換えられると考えます。
なぜ
画面の JavaScript による入力チェックは、ブラウザの開発者ツールや curl で簡単に迂回できます。「数値しか入らないはず」の欄に文字列が来て、SQL や処理が壊れるのが事故の入口です。
どうやって
サーバー側で、型（数値か文字列か）、長さ（上限）、範囲（0〜100 など）、形式（メールアドレス・日付）、許可リスト（選択肢はこの3つだけ）を検証します。禁止パターンを探す「ブラックリスト」ではなく、許す形を決める「許可リスト」で書きます。フレームワークのバリデーション機能（Django のフォーム、Spring の Bean Validation、zod など）を使います。
確かめ方
ブラウザを使わず curl で、想定外の値（負の数、長い文字列、別の利用者の ID）を直接送ってみる。サーバーが 400 系で拒否すれば OK。詳しくは 第3章 7.
RULE 2
文字列をつなげて命令を作らない（SQL・HTML・OS コマンド）
何を
SQL、HTML、OS コマンド、LDAP、ファイルパスなど「命令として解釈される文字列」に、利用者の入力を文字列連結で混ぜない。
なぜ
混ぜると、入力の中の記号（' や <script> や ;）が命令の一部として解釈され、データの窃取・改ざん（SQL インジェクション）、他の利用者のブラウザでのスクリプト実行（XSS）、サーバーでの任意コマンド実行につながります。インジェクションは OWASP Top 10:2025 の A05 で、昔から今まで消えていません。
どうやって
SQL はプレースホルダ（? や %s に値を別渡し）か ORM。HTML はテンプレートエンジンの自動エスケープに任せ、無効化する書き方（|safe、dangerouslySetInnerHTML、innerHTML）を使わない。OS コマンドは呼ばないのが最善で、どうしてもなら引数を配列で渡しシェルを経由しない。
確かめ方
リポジトリで "SELECT や f"SELECT、+ " WHERE、innerHTML、subprocess・exec( を検索し、入力が混ざっていないかを見る。詳しくは 第3章
RULE 3
認証は自分で作らない（標準機能か認証サービス、パスワードは bcrypt／Argon2、多要素認証）
何を
ログイン、パスワードの保存、パスワードリセット、セッション管理、多要素認証。
なぜ
認証は「正しく作るのが難しいのに、間違えると全員のアカウントが危ない」領域です。平文や MD5 でのパスワード保存、推測できるセッション ID、リセット用トークンの使い回しなど、自作で起きる事故が決まっています。
どうやって
フレームワーク標準の認証機能（Django の auth、Rails の Devise、Spring Security、ASP.NET Identity）か、外部の認証サービス（IDaaS）を使う。パスワードを自分で保存するなら bcrypt か Argon2 でハッシュする（SHA-256 単体は不可）。多要素認証を用意し、管理者には必須にする。
確かめ方
DB の users テーブルのパスワード列を見て、$2b$（bcrypt）や $argon2id$ で始まっていれば OK。平文・MD5・SHA-1 の16進数なら要修正。詳しくは 第4章 2.
RULE 4
「何をしてよいか」は毎回サーバーで確かめる（認可・デフォルト拒否）
何を
データの閲覧・変更・削除、管理機能、他の利用者に関わる操作。「ログインしているか」（認証）だけでなく「この人がこの対象にこの操作をしてよいか」（認可）。
なぜ
OWASP Top 10:2025 の1位は「アクセス制御の不備」です。「URL の /orders/123 を /orders/124 に変えたら他人の注文が見えた」「画面にボタンがないだけで、API を直接叩けば削除できた」が典型です。自動ツールでは見つけにくく、人が設計で決めるしかありません。
どうやって
権限の表（誰が・何に・何をしてよいか）を設計時に作る。すべての API で、対象データの所有者や役割をサーバー側で確認する。確認処理は1か所（ミドルウェアや共通関数）にまとめ、「書き忘れたら拒否される」構造（デフォルト拒否）にする。
確かめ方
利用者 A でログインしたまま、利用者 B のデータの ID を URL や API に入れてアクセスする。403 や 404 になれば OK。詳しくは 第4章 6.
💡イメージで理解する：入口の4つ

郵便受けに入れられた物を開封前に確かめ（1）、入っていた紙をそのまま命令書として実行せず（2）、玄関の鍵は専門メーカー製を使い（3）、入った人にも部屋ごとに入ってよいか確かめる（4）。

3. 宝を隠す：ルール 5〜6

RULE 5
秘密はコードに書かない（環境変数かシークレット管理、漏れたら即ローテーション）
何を
API キー、DB のパスワード、クラウドのアクセスキー、署名用の鍵、外部サービスのトークン。
なぜ
コードに書いた秘密は、リポジトリの履歴に永久に残り、非公開でもフォーク・CI のログ・退職者の手元・誤って公開への切り替え、で漏れます。公開リポジトリに入ったキーは数分でボットに拾われて悪用されます。
どうやって
環境変数か、クラウドのシークレット管理（AWS Secrets Manager、GCP Secret Manager、Vault）に置き、.env は .gitignore に入れる。.env.example にはキー名だけ書く。漏れたら「消す」ではなく無効化して新しい鍵に替える（ローテーション）。履歴から消しても、すでに取られた前提で動く。
確かめ方
リポジトリ全体を AKIA（AWS）、sk-、password=、BEGIN PRIVATE KEY などで検索する。gitleaks などのシークレットスキャンを CI に入れる。詳しくは 第5章 5.・6.
RULE 6
通信は全部 HTTPS、Cookie には Secure・HttpOnly・SameSite
何を
利用者とサーバーの間、サーバーと外部 API の間、サーバー同士の間の通信。ログイン状態を保つ Cookie。
なぜ
HTTP のままだと、同じ Wi-Fi にいる人や経路上の機器に、パスワードやセッション ID が丸見えで、書き換えもできます。Cookie に属性がないと、XSS でセッション ID を盗まれたり（HttpOnly なし）、HTTP に落とされて盗まれたり（Secure なし）、他サイトから勝手に送られたり（SameSite なし）します。
どうやって
証明書は無料の Let's Encrypt かクラウドの証明書サービスで取得し、自動更新にする。HTTP は HTTPS へ転送し、HSTS を付ける。セッション Cookie には Secure; HttpOnly; SameSite=Lax（または Strict）を付ける。
確かめ方
ブラウザの開発者ツールの「アプリケーション → Cookie」で属性を確認する。curl -I https://自分のサイト で Strict-Transport-Security があるか見る。詳しくは 第5章 2.・第4章 4.

4. 家を整える：ルール 7〜8

RULE 7
部品は最新に保つ（lock ファイル・自動更新・スキャン・EoL を使わない）
何を
ライブラリ、フレームワーク、言語のランタイム、OS、コンテナのベースイメージ、DB・ミドルウェア。
なぜ
脆弱性のニュースの大半は「自分が書いていないコード」の穴です（IPA 10大脅威 2026 の2位、OWASP A03）。穴が公表されると、修正版を当てていないシステムが世界中から自動で狙われます。EoL のものは直す版が出ないので、使い続けること自体が穴です。
どうやって
lock ファイル（package-lock.json、poetry.lock など）をコミットして、どの版を使っているかを確定させる。自動更新（Dependabot か Renovate）を有効にして PR を放置しない。スキャン（npm audit、pip-audit、Trivy）を CI に入れる。言語・フレームワークのサポート期限を把握し、EoL の前に上げる。
確かめ方
今すぐ npm audit か pip-audit を1回回す。High 以上が出たら、その部品を使っている箇所と外から届く経路を確かめる（第1章の3問）。詳しくは 第6章
RULE 8
必要最小限だけ開ける（ポート・公開設定・権限・管理画面は「閉」が初期値）
何を
ネットワークのポート、ストレージの公開設定、クラウドの権限（IAM）、管理画面・デバッグ機能、サービスアカウントの権限、CI のトークンの権限。
なぜ
OWASP A02「セキュリティ設定の不備」。DB をインターネットに直接公開、ストレージを「全員に公開」、管理画面が初期パスワードのまま、CI のトークンが全リポジトリに書き込み可能。どれも「開けすぎ」が原因で、ボットが数時間で見つけます。
どうやって
最小権限：その仕事に必要な権限だけを与える。デフォルト閉：公開・許可は明示的に必要なものだけ開ける。DB・キャッシュ・内部 API は外から到達できない位置に置く。管理画面は IP 制限や多要素認証で守る。本番でデバッグモードを切る。設定はコード（IaC）にして差分をレビューする。
確かめ方
外部から nmap（自分のサーバーに対してだけ）やクラウドの「公開アクセス」の警告で、開いているものを一覧にする。一覧にあるものすべてに「なぜ必要か」を書けるか。詳しくは 第7章
💡イメージで理解する：宝と家

合鍵をドアマットの下に置かず（5）、窓は曇りガラスにし（6）、欠陥が見つかった建材は交換し（7）、使わない勝手口は塞いでおく（8）。

5. 見張る：ルール 9〜10

RULE 9
記録は残す、秘密は残さない（ログとエラー表示）
何を
ログイン成功・失敗、権限の変更、データの削除・エクスポート、管理操作、エラー。これらを誰が・いつ・何にしたかの形で残す。逆に、パスワード・カード番号・トークン・個人情報の本体はログに書かない。
なぜ
OWASP A09「ログとアラートの不備」。記録がないと、攻撃されたことに気づけず、気づいても範囲が特定できません。一方で、ログに秘密を書くと、ログ基盤が第2の漏えい元になります。また、利用者に見せるエラーにスタックトレースや SQL を出すと、攻撃者に内部構造を教えることになります。
どうやって
構造化ログ（JSON）で、利用者 ID・操作・対象・結果・時刻を残す。パスワードやトークンはログ出力前にマスクする。利用者には「処理に失敗しました（問い合わせ番号 XXXX）」のような一般的な文を見せ、詳細はログに残す。ログイン失敗の急増など、異常にはアラートを付ける。
確かめ方
わざと失敗する操作をして、ログに「誰が何をしたか」が残っているか、画面に内部情報が出ていないかを見る。ログを password・token で検索して、値が入っていないか確かめる。詳しくは 第8章 2.
RULE 10
人の目と機械の目に乗せる（レビューの観点・CI の自動検査・設計時の1問）
何を
コードレビュー、CI、設計レビュー。「気をつける」ではなく、流れに組み込んで忘れても引っかかるようにする。
なぜ
人は忘れます。ルール 1〜9 を全員が毎回思い出すのは無理なので、PR テンプレートと自動検査で「思い出さなくても止まる」仕組みにします。設計の段階で「悪用されたら」を1回考えるだけで、後から直すと高くつく穴（認可の設計漏れ）を防げます。
どうやって
PR テンプレートに本サイトのチェックリストの該当項目を入れる。CI に依存スキャン・シークレットスキャン・静的解析（SAST）を入れる。設計レビューで「この機能が悪用されたら、誰が何を失うか」を1問必ず聞く。
確かめ方
直近の PR に、セキュリティ観点のチェックが1つでも付いているか。CI が止めた実績が1つでもあるか。詳しくは 第9章

6. よくある言い訳と、その返し

言い訳返し
「社内の人しか使わないシステムだから」内部不正は IPA 10大脅威 2026 の7位。フィッシングで社員の端末が乗っ取られれば、攻撃者は「社内の人」として入ってくる。認可とログは社内システムにこそ要る。
「誰もそんなことしない」人ではなくボットがする。インターネットに出した瞬間から、全アドレスを巡回するボットが既知の穴を自動で試す。
「フレームワークが守ってくれるはず」既定値は守ってくれる。守られないのは、既定値を外したとき（|safe、innerHTML、生 SQL）と、フレームワークが関知しない認可の設計。
「画面でチェックしているから」画面のチェックは利用者の操作ミスを防ぐため。攻撃者は画面を使わない（curl で直接送る）。
「リポジトリは非公開だから鍵を書いてもいい」履歴に永久に残る。フォーク・CI ログ・退職者・公開への誤切替で漏れる。漏れたら即ローテーションが要るが、どこに書いたか把握できていないと替えられない。
「時間がないので後で直す」後で直すほど高くつく（設計の穴は作り直し）。ルール 1〜10 のうち、今の PR で該当する1つだけでも守る。

7. 明日からの3手

今日（10分）依存スキャンを1回回す

npm audit、pip-audit、bundle audit など、自分の言語のコマンドを1回実行する。結果の High 以上を、第1章の3問で仕分けする。

今週（30分）秘密情報がリポジトリにないか検索する

AKIA、password=、BEGIN PRIVATE KEY、sk- などで全履歴を検索する。見つかったら、消すより先にローテーションする。

今月（1時間）チェックリストを PR テンプレートに入れる

本サイトのチェックリストの「実装のとき」を Markdown でコピーし、.github/pull_request_template.md に貼る。

🛠️実務ではこうする：レビューで言う一言
  • 「この値はサーバー側でも検証していますか？」（ルール 1）
  • 「この SQL、プレースホルダにできますか？」「この innerHTML、textContent ではだめですか？」（ルール 2）
  • 「このパスワード、bcrypt か Argon2 ですか？」（ルール 3）
  • 「他の利用者の ID を入れたら、どこで弾かれますか？」（ルール 4）
  • 「この鍵、環境変数に出せますか？」（ルール 5）
  • 「この Cookie、HttpOnly と SameSite は付いていますか？」（ルール 6）
  • 「lock ファイルは更新されていますか？ audit は通りましたか？」（ルール 7）
  • 「このポート／このバケット、外から見える必要がありますか？」（ルール 8）
  • 「このログ、トークンがそのまま出ていませんか？」（ルール 9）
  • 「この機能、悪用されたら誰が何を失いますか？」（ルール 10）
⚠️間違えやすい点
  • 「入力をエスケープしたから SQL は安全」→ エスケープ漏れが起きやすい。SQL はプレースホルダが正解で、エスケープは HTML 出力のときの話。
  • 「ハッシュ化しているから安全」→ MD5 や SHA-256 単体は高速に総当たりできる。パスワードにはbcrypt か Argon2（わざと遅いハッシュ）。
  • 「ログイン必須にしたから安全」→ それは認証。認可（誰がどのデータに）は別に要る。
  • 「秘密を履歴から消したから大丈夫」→ 取られた前提でローテーションが先。

入口を固める（疑う・つながない・作らない・確かめる）／宝を隠す（書かない・暗号化）／家を整える（最新に・閉じる）／見張る（残す・乗せる）。
画面側で入力チェックをしていれば、サーバー側は省いてよいですか。
だめ。画面のチェックは操作ミス防止で、攻撃者は curl などで直接送る。サーバー側で型・長さ・範囲・許可リストを検証する。
SQL・HTML・OS コマンドそれぞれで「文字列をつなげない」ための正解は？
SQL＝プレースホルダか ORM。HTML＝テンプレートの自動エスケープ（innerHTML や |safe を使わない）。OS コマンド＝呼ばない。呼ぶなら引数配列でシェルを経由しない。
パスワードの保存に使ってよいハッシュと、だめなものは？
よい＝bcrypt、Argon2（わざと遅い）。だめ＝平文、MD5、SHA-1、SHA-256 単体（高速に総当たりされる）。
認可の確認を「書き忘れても安全」にする構造は？確かめ方は？
確認を1か所（ミドルウェア・共通関数）にまとめ、許可がなければ拒否するデフォルト拒否にする。確かめ方は、利用者 A のまま利用者 B のデータ ID でアクセスし 403/404 になるか。
API キーをコードに書いてしまい、リポジトリは非公開です。何が問題で、見つけたらまず何をしますか。
履歴に永久に残り、フォーク・CI ログ・退職者・公開への誤切替で漏れる。見つけたら消すより先に、無効化して新しい鍵に替える（ローテーション）。
セッション Cookie に付ける3つの属性と、それぞれ何を防ぐか。
Secure（HTTP で送られるのを防ぐ）、HttpOnly（JavaScript から読まれる＝XSS で盗まれるのを防ぐ）、SameSite（他サイトから勝手に送られる＝CSRF を防ぐ）。
部品を最新に保つための4つの手段は？
lock ファイルをコミットして版を確定／自動更新（Dependabot・Renovate）／スキャン（npm audit・pip-audit・Trivy）を CI に／EoL の前に上げる。
「最小権限」と「デフォルト閉」とは？
最小権限＝その仕事に必要な権限だけを与える。デフォルト閉＝公開・許可は明示的に必要なものだけ開け、初期値は閉じる。
ログに残すべきものと、残してはいけないものは？
残す＝ログイン成否・権限変更・削除・エクスポート・管理操作を「誰が・いつ・何に」の形で。残さない＝パスワード・カード番号・トークン・個人情報の本体。
「明日からの3手」は？
今日：依存スキャンを1回回す。今週：秘密情報がリポジトリの履歴にないか検索する。今月：チェックリストを PR テンプレートに入れる。
