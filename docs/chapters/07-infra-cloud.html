第7章 サーバー・クラウド・ネットワークの設定

コードに穴がなくても、設定が開いていれば入られます。DB がインターネットから見える、ストレージが全員に公開、デバッグモードのまま本番、初期パスワードのまま。どれも「開けすぎ」が原因で、インターネット全体を巡回するボットが数時間で見つけます。この章では、ネットワーク・権限・ストレージ・応答ヘッダー・コンテナ・CI の「閉じ方」と、設定をコードにして差分で見る方法を扱います。

🧭この章で理解してほしいこと
  • 設定ミスの原因は「開けすぎ」：OWASP Top 10:2025 の A02「セキュリティ設定の不備」
    • 典型：DB をインターネットに公開、ストレージを全員に公開、デバッグモードのまま本番、初期パスワードのまま、管理画面やサンプルの放置、CORS の *
    • 見つけるのは人ではなくボット。公開した瞬間から全アドレスを巡回して試す
    • 対策の原則は2つ：最小権限（必要な権限だけ）とデフォルト閉（明示的に必要なものだけ開ける）
  • ネットワーク：外に開けるのは 443 だけ
    • DB・キャッシュ・内部 API は非公開ネットワークに置き、アプリからだけ届くようにする
    • ファイアウォール（セキュリティグループ）は許可リスト。0.0.0.0/0 で開けてよいのは 443（と HTTPS への転送用の 80）だけ
    • SSH はパスワード禁止・鍵認証・root ログイン禁止。外からは直接開けず、踏み台か SSM／IAP 経由
    • VPN・リモート接続機器のパッチは最優先（IPA 10大脅威 2026 の8位）
  • クラウドの権限：人には SSO とロール、サービスにはロール
    • アクセスキーをサーバーやコードに置かない。実行環境のロール（インスタンスロールなど）を使う
    • ルートアカウントは MFA を付けて金庫に。日常では使わない
    • "Action": "*" のポリシーは使わない。キーは定期的に棚卸しして消す
  • ストレージ：パブリックアクセスブロックを ON
    • 公開してよいのは静的サイトの配信だけ。それも CDN 経由にしてバケット自体は閉じる
    • 一時的に渡したいファイルは、有効期限付きの署名付き URL で
    • バケット名は推測される前提。「名前を知らなければ見えない」は守りにならない
  • 応答ヘッダー：7つを付けて curl -I で確かめる
    • HSTS（HTTPS 固定）、CSP（読み込み元の制限）、X-Content-Type-Options: nosniff、frame-ancestors（埋め込み禁止）、Referrer-Policy、Permissions-Policy、機密ページの Cache-Control: no-store
    • Express なら helmet、nginx なら add_header。CSP はまず Report-Only で始める
    • WAF と CDN は保険。根本対策はコードと設定。ログインや API にはレート制限
  • コンテナ：root で動かさない・読み取り専用・秘密を焼かない
    • Dockerfile に USER を書く。ベースイメージはタグを固定し、定期的に更新する
    • 秘密は ENV にも ARG にも書かない。.dockerignore で .env や .git を除外する
    • 実行時は読み取り専用ファイルシステム、不要な権限（capability）を落とす
  • CI：トークンの権限を最小に、Action はコミット SHA で固定
    • GitHub Actions は permissions: を明示して最小にする
    • フォークからの PR にシークレットを渡さない。pull_request_target で PR のコードを実行しない
    • シークレットを echo や変換して出さない。開発機は OS 更新・ディスク暗号化・画面ロック
  • 設定はコード（IaC）にして差分で見る：Checkov・tfsec・Trivy で自動検査、手で変えた差分（ドリフト）を検知する

読み終えたら、本文を見ずに各項目を自分の言葉で説明できるか確かめてください。

1. 設定ミスが事故になる：典型例とボット

OWASP Top 10:2025 の A02 は「セキュリティ設定の不備」です。コードの穴と違って、フレームワークやクラウドが用意した機能を「開けたまま」にしているだけで事故になります。しかも設定は目に見えにくく、レビューの対象から漏れがちです。

典型的な設定ミス何が起きるか正しい状態
DB・キャッシュがインターネットから接続できるパスワード総当たり、認証なしの DB（既定で認証がないものもある）からデータを丸ごと取られる非公開ネットワークに置き、アプリのサーバーからだけ接続できる（2節）
ストレージを「全員に公開」顧客の書類・バックアップ・ログが誰でもダウンロードできるパブリックアクセスブロック ON、署名付き URL（4節）
デバッグモードのまま本番エラー画面にソースコード・環境変数・DB の接続情報が表示される本番ではデバッグを無効化し、環境変数で切り替える
初期パスワード・既定の管理者アカウントのまま製品のマニュアルに載っているパスワードで管理画面に入られる初回に変更。可能なら既定アカウントを無効化
ディレクトリ一覧表示・サンプルページ・管理画面の放置内部のファイル名や、脆弱性のあるサンプルが攻撃の足がかりになる一覧表示を無効化、使わないものは削除、管理画面は IP 制限か MFA
CORS で * を許可どのサイトからでも API を呼ばれ、利用者のデータを他サイトが読める許可するオリジンを列挙する
詳細なエラーをそのまま返すスタックトレースや SQL から内部構造・ライブラリの版が分かり、次の攻撃に使われる利用者には一般的な文、詳細はログへ（第8章）
✗ 危険な例：本番でもデバッグ ON、CORS は全開
Python（Django settings.py）／ Express# settings.py
DEBUG = True
ALLOWED_HOSTS = ["*"]

// Express
const cors = require("cors");
app.use(cors());  // どのオリジンからでも許可
エラー画面に環境変数や SQL が出る。API がどのサイトからでも呼べる。
✓ 安全な例：環境変数で切り替え、許可元を列挙
Python（Django settings.py）／ Express# settings.py
import os
DEBUG = os.environ.get("DJANGO_DEBUG") == "1"
ALLOWED_HOSTS = ["app.example.com"]

// Express
app.use(cors({
  origin: ["https://app.example.com"],
  credentials: true
}));
本番では DJANGO_DEBUG を設定しないので既定で OFF。API を呼べるのは自分のフロントだけ。
💡イメージで理解する

玄関に高価な鍵（コードの対策）を付けても、裏口が開けっぱなし（設定）なら意味がありません。しかも、泥棒は一軒ずつ下見するのではなく、町中のドアノブを自動で回して回る機械（ボット）を使っています。「うちは小さいから狙われない」は通用せず、開いているドアは順番に見つかります。

🔑覚え方：「最小権限」と「デフォルト閉」

この章の全節は2つの原則に戻ります。最小権限＝その仕事に必要な権限・経路だけを与える。デフォルト閉＝初期値は閉じておき、必要なものだけ理由を書いて開ける。「なぜこれは開いているのか」に一文で答えられない設定は、閉じる候補です。

2. ネットワーク：公開するもの・しないもの、SSH

ネットワークの設計は、インターネットから直接届く層を最小にすることに尽きます。利用者が届く必要があるのはロードバランサ（または WAF・CDN）だけで、アプリ・DB は後ろに隠します。

外から届くのは一番手前の層だけ。DB は非公開ネットワークに置く
インターネット
利用者
ボット・攻撃者
公開層（443 だけ開ける）
ロードバランサWAF・CDN
→
アプリ
非公開ネットワーク
DB
キャッシュ

赤の層から直接届くのは橙の層のロードバランサだけ。アプリは「ロードバランサから」、DB は「アプリから」だけ接続を受け付ける。
対象インターネットに開ける？許可元
ロードバランサ・WAF・CDN開ける（443。80 は HTTPS への転送だけ）0.0.0.0/0
アプリのサーバー開けないロードバランサのセキュリティグループだけ
DB・キャッシュ・メッセージキュー開けないアプリのセキュリティグループだけ
SSH（22）・RDP（3389）開けない踏み台サーバー、または SSM Session Manager／IAP のような経由サービス。開けるなら自社の固定 IP だけ
管理画面・監視ツール開けないVPN 経由、または IP 制限＋MFA
✗ 危険な例：DB を全世界に開けている
Terraform（AWS セキュリティグループ）resource "aws_security_group" "db" {
  ingress {
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
「パスワードがあるから大丈夫」ではない。総当たりと、DB 自体の脆弱性が直接狙われる。
✓ 安全な例：アプリのグループからだけ
Terraform（AWS セキュリティグループ）resource "aws_security_group" "db" {
  ingress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]
  }
}
許可元を「アプリのサーバー」というグループで指定する。IP が変わっても追従する。

SSH は鍵認証、root 禁止、外から直接開けない

✗ 危険な例：パスワードで root ログイン可
/etc/ssh/sshd_configPermitRootLogin yes
PasswordAuthentication yes
Port 22   # しかも 0.0.0.0/0 に開放
公開された SSH は数分で総当たりが始まる。root で入られたら全部終わり。
✓ 安全な例：鍵だけ、root 禁止
/etc/ssh/sshd_configPermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
# 設定を反映
# sudo systemctl reload sshd
鍵認証は総当たりが現実的に不可能。さらに外から直接開けず、踏み台か SSM／IAP を経由する。

VPN やリモートデスクトップの機器そのものの脆弱性を突く攻撃は、IPA 10大脅威 2026 の8位「リモートワーク等の環境や仕組みを狙った攻撃」です。入口の機器のパッチは、アプリより先に当てます。

🛠️実務ではこうする：開いているものを一覧にする
  • サーバーの中から：ss -tlnp（Linux）で待ち受けているポートを一覧にし、1つずつ「なぜ必要か」を書く。
  • クラウドのコンソールから：セキュリティグループで 0.0.0.0/0 を含むルールを検索する。443 以外があれば理由を確認する。
  • 外から：自分の管理下にあるサーバーに対してだけ、nmap のようなポートスキャンで外から見える状態を確認する。
⚖️ポートスキャンは自分のサーバーだけ

他人のサーバーや、勤務先でも許可を得ていないサーバーにポートスキャンや接続の試行をしてはいけません。不正アクセス禁止法などに触れるおそれがあり、「確認のつもり」でも通りません。

3. クラウドの権限：最小権限とロール

クラウドでは、ネットワークの穴より権限の穴のほうが大きな事故になります。長期間有効なアクセスキーが漏れると、攻撃者は正規の API で何でもできるからです。考え方は AWS でも GCP でも Azure でも同じです。

対象やってはいけない正しいやり方
人全員が管理者権限。ルートアカウントを共有SSO（IAM Identity Center など）で個人を識別し、役割ごとのロールに割り当てる。ルートアカウントは MFA を付けて日常では使わない
サーバー・コンテナ・関数アクセスキーを .env やコードに置く実行環境にロールを付ける（インスタンスロール、タスクロール、サービスアカウント）。鍵は自動で発行・更新される
CI管理者権限の長期キーをシークレットに登録OIDC 連携で CI の実行ごとに短期の認証情報を得る。権限はデプロイ対象だけ
鍵全般作りっぱなし。退職者の鍵が残る90日などの周期で棚卸しし、使っていない鍵は消す。「最終使用日」を確認する
✗ 危険な例：何でもできるポリシー
IAM ポリシー（JSON）{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "*",
    "Resource": "*"
  }]
}
この権限を持つ鍵が漏れたら、全データの削除も、他リージョンでの暗号資産マイニングも可能。
✓ 安全な例：必要な操作と対象だけ
IAM ポリシー（JSON）{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::app-uploads/*"
  }]
}
このアプリが使うバケットの読み書きだけ。漏れても被害はそのバケットに限られる。

IAM のユーザー・グループ・ポリシー・ロールの基本は AWS 合格ノート 第2章 にまとまっています。

⚠️間違えやすい点
  • 「鍵は非公開リポジトリにあるから安全」→ 第5章のとおり、履歴・CI ログ・端末から漏れる。鍵を置かない設計（ロール）が正解。
  • 「開発環境だから管理者権限でいい」→ 開発環境の鍵が漏れて本番に横移動する事故は珍しくない。環境ごとにアカウントを分ける。

4. ストレージの公開設定

オブジェクトストレージ（S3、Cloud Storage、Blob Storage）の公開設定ミスは、顧客情報の大量漏えいとして最も多く報じられる事故の一つです。原因はほぼ毎回「バケットかオブジェクトを全員に公開していた」です。

📰ニュースではこう報じられる

「クラウドのストレージ設定ミスにより、顧客情報〇万件が第三者から閲覧可能な状態になっていた。外部からの指摘で判明。」

  • 「設定ミス」→ ほぼ必ず、公開設定（ACL かバケットポリシー）が「全員」になっていた
  • 「閲覧可能な状態」→ 実際に取られたかは不明でも、公開されていた期間は「取られた前提」で報告義務の判断をする（第8章 7.）
  • 「外部からの指摘で判明」→ 自分では気づけなかった＝公開状態を検知する仕組みがなかった
やりたいことやってはいけない正しいやり方
利用者がアップロードした書類を保管するバケットを公開して URL を知っている人だけ見る運用バケットは非公開。アプリが認可を確認したうえで署名付き URL（有効期限 数分〜1時間）を発行する
静的サイト・画像を配信するバケットを公開して直接配信CDN（CloudFront など）経由で配信し、バケットは CDN からだけ読めるようにする
バックアップ・ログを置く同じアカウント・同じ権限で読み書き別アカウントか別の権限で、書き込み専用＋バージョニング＋オブジェクトロック（第8章 4.）
✗ 危険な例：公開バケットに置いて URL を配る
Python（boto3）s3.upload_file(path, "app-uploads", key,
    ExtraArgs={"ACL": "public-read"})
url = f"https://app-uploads.s3.amazonaws.com/{key}"
# 「URL を知っている人だけ」は守りにならない
バケット名もキーも推測・列挙される。公開した瞬間から全世界から読める。
✓ 安全な例：非公開のまま、期限付きの URL を発行
Python（boto3）s3.upload_file(path, "app-uploads", key)  # 既定は非公開
# 認可（この利用者がこのファイルを見てよいか）を確認してから
url = s3.generate_presigned_url(
    "get_object",
    Params={"Bucket": "app-uploads", "Key": key},
    ExpiresIn=600)  # 10分で失効
バケットは閉じたまま。URL が漏れても10分で使えなくなる。
🛠️実務ではこうする：公開を「できなくする」
  • S3 ならパブリックアクセスブロックの4つ（BlockPublicAcls・IgnorePublicAcls・BlockPublicPolicy・RestrictPublicBuckets）をアカウント全体で ON にする。これで誰かが誤って公開しようとしても弾かれる。
  • コンソールの「パブリック」バッジや、aws s3api get-public-access-block --bucket <名前> で確認する。
  • 公開配信が本当に必要なバケットだけ例外にし、理由を IaC のコメントに書く。

5. セキュリティヘッダーと WAF・レート制限

サーバーが返す HTTP の応答ヘッダーには、「このサイトではこう振る舞え」とブラウザに指示するものがあります。付けるだけで、XSS・クリックジャッキング・HTTP への格下げなど複数の攻撃の被害を抑えられます。

ヘッダー何をするか推奨値の例
Strict-Transport-Security
HSTS		以後このサイトには HTTPS でだけ接続するようブラウザに記憶させるmax-age=31536000; includeSubDomains
Content-Security-Policy
CSP		スクリプト・画像などの読み込み元を制限する。XSS の被害を抑える最後の砦まず Content-Security-Policy-Report-Only で default-src 'self' から始め、違反の報告を見ながら本番化する
X-Content-Type-Optionsブラウザが Content-Type を勝手に推測して実行するのを止めるnosniff
frame-ancestors（CSP）
旧 X-Frame-Options		他サイトの iframe に埋め込まれるのを禁止する（クリックジャッキング対策。第4章）frame-ancestors 'none'（旧：X-Frame-Options: DENY）
Referrer-Policyリンク先に自分の URL（トークン付きのことも）を送りすぎないstrict-origin-when-cross-origin
Permissions-Policyカメラ・マイク・位置情報など、使わない機能を無効化するcamera=(), microphone=(), geolocation=()
Cache-Control機密ページをブラウザや中継機器にキャッシュさせないログイン後のページに no-store
✗ 不足している例：ヘッダーなし
curl -I https://app.example.comHTTP/2 200
content-type: text/html; charset=utf-8
server: nginx/1.24.0
# HSTS も CSP も nosniff もない
# server ヘッダーで版まで教えている
HTTP に落とされる、他サイトに埋め込まれる、XSS が成立したら何でも読み込まれる。
✓ 安全な例：nginx と Express（helmet）
nginx.conf ／ Express# nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options nosniff always;
add_header Content-Security-Policy "default-src 'self'; frame-ancestors 'none'" always;
server_tokens off;

// Express：helmet が主要ヘッダーをまとめて付ける
const helmet = require("helmet");
app.use(helmet());
helmet の既定値で HSTS・nosniff・frame-ancestors などが付く。CSP は自サイトの構成に合わせて調整する。

確認は curl -I https://自分のサイト で応答ヘッダーを見るだけです。ブラウザの開発者ツールの「ネットワーク」タブでも見られます。

WAF・DDoS 対策・レート制限は「保険」

WAFWeb Application Firewall
リクエストの内容を規則で検査し、SQL インジェクションや XSS らしきものを遮断する。すり抜けは必ずあるので、コード側の対策（第3章）の代わりにはならない。パッチを当てるまでの時間稼ぎ（仮想パッチ）としては有効。
CDN・DDoS 対策Content Delivery Network
大量の通信を手前で受け止める。DDoS（IPA 10大脅威 2026 の9位）は自前のサーバーでは防げないので、CDN やクラウドの DDoS 対策サービスに任せる。
レート制限Rate Limiting
同じ IP や利用者からの回数を制限する。ログイン・パスワードリセット・公開 API に必須（第4章 3.）。nginx の limit_req、Express の express-rate-limit、API ゲートウェイの機能などで実現する。
⚠️間違えやすい点

「WAF を入れたから SQL インジェクション対策は済み」は誤りです。WAF は既知のパターンにしか反応せず、迂回手法も多数あります。根本対策はプレースホルダ（第3章）、WAF は二重目の保険です。

6. コンテナと実行環境

コンテナは「分離されているから安全」と思われがちですが、root で動かす・秘密をイメージに焼く・古いベースイメージを使い続けると、コンテナの外まで被害が広がります。

✗ 危険な Dockerfile
DockerfileFROM node:latest
WORKDIR /app
COPY . .                 # .env も .git も入る
ENV API_KEY=sk-xxxxxxxx  # イメージに永久に残る
RUN npm install
CMD ["node", "server.js"]  # root で実行
latest は再現性がなく、ENV／ARG の秘密は docker history で読める。root で動くとコンテナ脱出時の被害が大きい。
✓ 安全な Dockerfile

COPY package*.json ./
RUN npm ci --omit=dev
COPY src ./src                 # 必要なものだけ
USER node                      # 公式イメージにある非 root ユーザー
CMD ["node", "src/server.js"]
# 秘密は実行時に環境変数かシークレットで渡す

# .dockerignore
.env
.git
node_modules
秘密はイメージに入らない。非 root で動く。入るファイルを限定する。
実行時の設定DockerKubernetes（securityContext）
非 root で動かすDockerfile の USER、または --user 1000runAsNonRoot: true

ベースイメージと OS パッケージの脆弱性は、trivy image <イメージ名> のようなスキャンで見つけられます（第6章 8.）。

7. ローカルと CI の安全

CI はデプロイの権限を持つので、攻撃者から見れば「本番への近道」です。特に公開リポジトリでは、フォークからの PR で送られてきたコードを、シークレット付きで実行してしまう事故が起きます。

✗ 危険な例：権限が広く、Action の中身が固定されていない
.github/workflows/ci.ymlon: pull_request_target   # 外部 PR でもシークレットが使える
jobs:
  build:
    runs-on: ubuntu-latest
    # permissions の指定なし（既定はリポジトリ設定次第）
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}
      - uses: someone/useful-action@v3   # タグは後から差し替えられる
      - run: echo "${{ secrets.DEPLOY_TOKEN }}" | base64
外部の人が PR に書いたコードが、本番用のトークン付きで動く。タグ @v3 の中身が改ざんされても気づけない。変換して出力すると、ログのマスクが効かない。
✓ 安全な例：最小権限、SHA 固定、外部 PR にシークレットを渡さない
.github/workflows/ci.ymlon: pull_request   # 外部 PR ではシークレットが渡らない
permissions:
  contents: read   # 必要な権限だけ明示
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<40桁のコミット SHA>  # v4 相当。SHA で固定
      - uses: someone/useful-action@<40桁のコミット SHA>
      - run: npm ci && npm test
# デプロイは main への push だけで動く別ワークフローにし、
# クラウドの認証は長期キーでなく OIDC 連携で短期の認証情報を得る
テストとデプロイを分け、デプロイ側だけが権限を持つ。Action は SHA で固定し、Dependabot で更新する。
場所やること
GitHub Actionspermissions: を最小に。サードパーティ Action はコミット SHA で固定。pull_request_target で PR のコードをチェックアウトしない。シークレットを echo・変換・ファイル出力しない。リポジトリ設定で「フォークからの PR のワークフローは承認制」にする
開発機.env は .gitignore に。~/.aws/credentials に長期キーを置かず、SSO（aws sso login など）で短期の認証情報を使う。OS とブラウザの自動更新、ディスク暗号化（BitLocker／FileVault）、画面ロック、パスワードマネージャー
リポジトリブランチ保護（main への直接 push 禁止、レビュー必須）、シークレットスキャンと Dependabot を有効化（第6章・第9章）

8. 設定をコードにして差分を見る（IaC）

ここまでの設定を手作業（コンソールのクリック）でやると、「誰がいつ何を開けたか」が残らず、レビューもできません。IaC にすると、設定の変更がPR の差分になり、コードと同じようにレビューと自動検査に乗せられます（第2章ルール10）。

STEP 1コードにする

Terraform・CloudFormation・Pulumi などで、ネットワーク・権限・ストレージの設定を書く。手作業の変更を禁止する。

STEP 2差分をレビューする

PR で 0.0.0.0/0・"Action": "*"・acl = "public-read" のような文字列を探す。「なぜ開けるか」をコメントに書かせる。

STEP 3自動検査を CI に入れる

checkov -d .、tfsec .、trivy config . のような設定スキャンが、公開 DB や暗号化なしのストレージを PR の段階で止める。

STEP 4ドリフトを検知する

コードと実際の設定のずれ（ドリフト）を terraform plan の定期実行や、クラウドの設定監査（AWS Config、Security Hub、Security Command Center など）で見つける。

🛠️実務ではこうする：レビューで言う一言
  • 「この 0.0.0.0/0、443 以外で必要な理由は何ですか？」
  • 「この DB、アプリのセキュリティグループからだけにできますか？」
  • 「このアクセスキー、ロールに置き換えられますか？」
  • 「このバケット、パブリックアクセスブロックは ON ですか？ 公開が必要なら CDN 経由にできますか？」
  • 「curl -I で HSTS と nosniff は出ますか？」
  • 「この Dockerfile、USER はありますか？ .env は .dockerignore に入っていますか？」
  • 「この Action、SHA で固定できますか？ permissions は書いてありますか？」
📝用語の補足
ポート
通信の窓口の番号。443 は HTTPS、22 は SSH、5432 は PostgreSQL。開いているポートは攻撃の入口になりうる。
セキュリティグループ
クラウドの仮想ファイアウォール。どこから（IP かグループ）どのポートへの通信を許可するかを決める。
踏み台サーバー
外から直接 SSH させず、いったん経由させる専用サーバー。SSM Session Manager や IAP のような「踏み台不要」のサービスで置き換えられる。
CORS
別のオリジンの Web ページから API を呼ぶことをブラウザに許可する仕組み。許可元は列挙する。
CDN
利用者に近い場所から配信するネットワーク。大量の通信を手前で受け止めるので DDoS 対策にもなる。
OIDC 連携
CI がクラウドに対して「私はこのリポジトリのこのワークフローです」と証明し、長期キーなしで短期の認証情報を得る仕組み。
仮想パッチ
コードを直す前に、WAF の規則で該当の攻撃パターンだけを遮断して時間を稼ぐこと。

🧠 想起練習

本文を見ずに答えを思い出してから、各項目を開いて確認してください。

設定ミスの典型例を5つ挙げてください。
DB をインターネットに公開、ストレージを全員に公開、デバッグモードのまま本番、初期パスワードのまま、管理画面・サンプルの放置（ほかに CORS の *、詳細なエラー表示）。
インターネットに開けてよいポートと、DB・SSH の許可元は？
開けるのは 443（と転送用の 80）だけ。DB はアプリのセキュリティグループからだけ。SSH は外から直接開けず、踏み台か SSM／IAP 経由。
「DB にパスワードがあるからインターネットに公開しても大丈夫」はなぜ誤りですか。
総当たりと DB 自体の脆弱性が直接狙われる。認証がない既定設定の DB もある。非公開ネットワークに置くのが正解。
SSH の設定で変える3つは？
PermitRootLogin no、PasswordAuthentication no、PubkeyAuthentication yes。さらに外から直接開けない。
サーバーからクラウド API を呼ぶとき、アクセスキーを置く代わりにどうしますか。
実行環境にロール（インスタンスロール・タスクロール・サービスアカウント）を付ける。鍵は自動で発行・更新される。
S3 のパブリックアクセスブロックの4つの設定は？どの範囲で ON にしますか。
BlockPublicAcls、IgnorePublicAcls、BlockPublicPolicy、RestrictPublicBuckets。アカウント全体で ON にする。
利用者に一時的にファイルを渡すとき、バケットを公開せずにどうしますか。
認可を確認したうえで、有効期限付きの署名付き URL を発行する（数分〜1時間）。
付けるべきセキュリティヘッダーを5つ以上挙げてください。確認コマンドは？
Strict-Transport-Security、Content-Security-Policy（frame-ancestors を含む）、X-Content-Type-Options: nosniff、Referrer-Policy、Permissions-Policy、機密ページの Cache-Control: no-store。確認は curl -I。
WAF は SQL インジェクション対策の代わりになりますか。
ならない。既知のパターンにしか反応せず迂回もある。根本対策はプレースホルダで、WAF は保険（仮想パッチ）。
Dockerfile で守る3点は？
タグを固定したベースイメージを定期更新する／USER で非 root にする／秘密を ENV・ARG に書かず、.dockerignore で .env と .git を除外する。
GitHub Actions で守る3点は？
permissions: を最小に明示／サードパーティ Action はコミット SHA で固定／pull_request_target で外部 PR のコードを実行しない（シークレットを渡さない）。
IaC にすると何ができるようになりますか。ドリフトとは？
設定変更が PR の差分になり、レビューと自動検査（Checkov・tfsec・Trivy）に乗せられる。ドリフトはコードと実際の設定のずれで、手作業の変更で起きる。
