第4章 認証・セッション・認可の脆弱性

「誰か」を確かめる認証、「さっきの人だ」を覚えておくセッション、「何をしてよいか」を決める認可。この3つは Web アプリの背骨で、どれか1つが抜けると全利用者のデータが危なくなります。この章では、パスワードの保存・総当たり対策・Cookie の属性・CSRF・認可の不備（OWASP Top 10:2025 の1位）・JWT の注意点を、危険なコードと安全なコードで見ていきます。

🧭この章で理解してほしいこと
  • 認証はフレームワーク標準か認証サービスを使い、自作しない
    • パスワードは bcrypt か Argon2id でハッシュして保存。平文・MD5・SHA-256 単体は高速に総当たりされる
    • ポリシーは長さ重視（8文字以上、15文字以上を推奨、上限は64文字以上）。記号の強制と定期変更の強要はしない（NIST SP 800-63B）。漏えいパスワードリストと照合する
    • 失敗メッセージは「ID かパスワードが違います」に統一。リセットは推測できない使い捨てトークン＋短い有効期限
  • 総当たりとパスワードリスト攻撃にはレート制限と多要素認証
    • アカウントロックだけだと「他人をロックする DoS」になる。遅延・CAPTCHA・IP とアカウント両方で制限
    • 多要素認証：TOTP アプリは標準、パスキー（FIDO2）はフィッシング耐性あり、SMS は弱い。管理者は必須
  • セッション ID はフレームワークに作らせ、ログイン成功時に再発行し、ログアウトでサーバー側で破棄する。URL には入れない
  • Cookie には Secure・HttpOnly・SameSite=Lax を付ける。__Host- プレフィックスでさらに固める
    • Secure：HTTP で送られない／HttpOnly：JavaScript から読めない（XSS で盗まれない）／SameSite：他サイトから勝手に送られない（CSRF）
  • CSRF は「ブラウザが Cookie を自動で付ける」から起きる。SameSite=Lax ＋ フレームワークの CSRF トークンで防ぎ、状態を変える操作は GET にしない
  • 認可は毎回サーバーで確かめ、確認を1か所に集め、デフォルト拒否にする（OWASP Top 10:2025 の1位）
    • IDOR：URL の ID を変えたら他人のデータ。クエリに所有者条件（AND user_id = ?）を含める
    • 垂直の権限昇格：一般利用者が管理 API を叩ける。役割の確認をミドルウェアで
    • マスアサインメント：JSON に is_admin: true を混ぜる。受け取る項目を許可リストに
    • 確かめ方：利用者 A のまま利用者 B の ID でアクセスし、403 か 404 になるか
  • JWT・OAuth は自作せずライブラリに任せ、署名アルゴリズムと有効期限を必ず検証する。トークンは localStorage に置かない（XSS で盗まれる）。短命＋リフレッシュ
  • クリックジャッキングは frame-ancestors、オープンリダイレクトは戻り先を相対パスか許可リストに

読み終えたら、本文を見ずに各項目を自分の言葉で説明できるか確かめてください。

2. パスワードの扱い：保存・ポリシー・リセット

保存：わざと遅いハッシュを使う

何が起きるか：DB が漏えいしたとき（SQL インジェクション、バックアップの流出、内部不正）、パスワードが平文なら全員のパスワードがそのまま漏れます。MD5 や SHA-256 でハッシュしていても、これらは高速に計算できるよう設計されているため、GPU で1秒間に数十億回の試行ができ、よくあるパスワードは短時間で元に戻されます。利用者はパスワードを使い回しているので、他のサービスでも被害が広がります。

どう防ぐか：パスワード専用の、わざと遅く設計されたハッシュ関数を使います。bcrypt か Argon2id です。どちらもソルトを自動で付け、結果の文字列に埋め込みます。

✗ 危険な例：高速なハッシュ・平文
Pythonimport hashlib
# 平文はもちろん、これも不可。1秒に数十億回試せる
stored = hashlib.sha256(password.encode()).hexdigest()
# 「ソルトを付けた SHA-256」も速さは変わらないので不十分
速いハッシュは「改ざん検知」用で、パスワード用ではありません。
✓ 安全な例：bcrypt／Argon2id
Python（bcrypt）import bcrypt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt())   # 保存する値（$2b$...）
ok = bcrypt.checkpw(password.encode(), hashed)              # 照合
Python（argon2-cffi）from argon2 import PasswordHasher
ph = PasswordHasher()
hashed = ph.hash(password)        # $argon2id$...
ph.verify(hashed, password)        # 違えば例外
JavaScript（bcrypt）const hash = await bcrypt.hash(password, 12);
const ok = await bcrypt.compare(password, hash);
フレームワーク標準の認証（Django の make_password、Rails の has_secure_password、Spring Security の PasswordEncoder）はこれを内蔵しています。自分で書くより、まず標準機能を使います。
🔑覚え方：DB を見れば分かる

users テーブルのパスワード列が $2b$12$…（bcrypt）や $argon2id$v=19$…（Argon2）で始まっていれば OK。64 文字の16進数なら SHA-256 の疑い、32 文字なら MD5 の疑い、読める文字なら平文。これだけで既存システムの危険度が分かります。

ポリシー：長さを重視し、無理な規則で弱くしない

米国 NIST の指針（SP 800-63B）は、現在は次の方針です。

  • 長さ：8文字以上を必須にし、15文字以上を推奨する。上限は少なくとも64文字（長いパスフレーズを許す）。
  • 記号・大文字の強制はしない：「P@ssw0rd」のような予測しやすい変形を生むだけ。
  • 定期変更の強要はしない：「末尾の数字を1つ増やす」運用を生む。漏えいの疑いがあるときに変更させる。
  • 漏えいパスワードリストと照合する：過去に流出したパスワードや「password123」のような常連は拒否する（Have I Been Pwned の Pwned Passwords API は、ハッシュの先頭5文字だけ送る方式で照合できる）。
  • 貼り付けを禁止しない：パスワードマネージャーの利用を妨げない。

リセットと失敗メッセージ：存在を悟らせない

✗ 危険な例
擬似コードif not user:
    return "このメールアドレスは登録されていません"
if not check(password):
    return "パスワードが違います"
# リセット用トークン
token = str(user.id) + str(int(time.time()))   # 推測できる
メッセージの違いで「どのメールアドレスが登録済みか」が分かり、総当たりの的が絞れます。推測できるトークンは他人のパスワードを書き換えられます。
✓ 安全な例
Pythonimport secrets, hashlib
from datetime import datetime, timedelta
# 失敗の理由は区別しない
if not user or not bcrypt.checkpw(pw, user.pw_hash):
    return "ID かパスワードが違います"

# リセット：推測不能・使い捨て・短命。DB にはハッシュを保存
token = secrets.token_urlsafe(32)
save(user.id, hashlib.sha256(token.encode()).hexdigest(), expires=datetime.now() + timedelta(minutes=30))
send_mail(user.email, f"https://example.com/reset?token={token}")
リセット依頼の応答も「登録があればメールを送りました」に統一します。トークンは1回使ったら無効化し、使用時に古いセッションも全部破棄します。

3. 総当たり・パスワードリスト攻撃と多要素認証

何が起きるか

総当たり（ブルートフォース）は、1つのアカウントに対して多数のパスワードを試す攻撃です。パスワードリスト攻撃（クレデンシャルスタッフィング）は、他のサービスから漏れた「ID とパスワードの組」のリストを、そのまま自分のサイトに試す攻撃です。利用者の多くがパスワードを使い回しているため、正しいパスワードで1回目に成功します。ニュースの「不正ログイン〇万件」の多くはこれです。

📰ニュースではこう報じられる

「〇〇で不正ログインが発生し、ポイント〇万円分が不正利用された。他社から流出した ID とパスワードを使ったパスワードリスト攻撃とみられる。同社のシステムからの漏えいは確認されていない」。読み方：利用者側の対策は使い回しをやめ、多要素認証を有効にすること。開発者側の課題は、1回目で成功するログインを止めるのは難しいので、多要素認証の提供、いつもと違う端末・場所からのログイン通知、漏えいパスワードとの照合、で被害を限定することです。

どう防ぐか：レート制限

  • アカウント単位：同じ ID への失敗が続いたら、回数に応じて待ち時間を伸ばす（1秒 → 2秒 → 4秒 …）、または CAPTCHA を出す。
  • IP 単位：同じ送信元から多数の ID への試行を制限する（パスワードリスト攻撃は ID を変えて来る）。
  • 通知：失敗の急増をアラートに（第8章）、新しい端末からのログイン成功を利用者にメールで知らせる。
⚠️間違えやすい点：「5回失敗で30分ロック」の罠

固定回数での完全ロックは、攻撃者がわざと失敗して他人をロックアウトする（サービス妨害）道具になります。管理者アカウントの ID が推測できれば、管理者を締め出せます。完全ロックではなく、遅延・CAPTCHA・本人への通知を組み合わせ、ロックするなら一時的で本人が解除できる形にします。

多要素認証（MFA）

パスワード（知っているもの）に、もう1つ別の種類の要素（持っているもの・本人の特徴）を組み合わせます。パスワードが漏れても、それだけではログインできなくなります。

方式強さ備考
認証アプリ（TOTP）標準30秒ごとに変わる6桁の数字。Google Authenticator 等。実装はライブラリ（pyotp、otplib）で。
パスキー／セキュリティキー（FIDO2・WebAuthn）最も強いサイトのドメインに紐づく鍵で署名するため、偽サイトでは使えない（フィッシング耐性）。管理者に向く。
SMS・メールのコード弱いSIM の乗っ取りや、偽サイトでコードを中継するフィッシングで突破される。無いよりは良い。

管理者と、金銭・個人情報に触れる操作には必須にします。一般利用者には提供して有効化を促し、バックアップコードを用意します。自作せず、フレームワークのプラグインか認証サービスを使います。

4. セッション管理と Cookie の属性

セッション ID の扱い

ログイン後、サーバーは「この人は認証済み」を覚えるためにセッション ID を発行し、Cookie に入れます。以降のリクエストは、この ID だけで本人と見なされます。つまりセッション ID を盗まれる＝パスワードなしでなりすまされるです。

決まりなぜ
ID はフレームワークに生成させる十分に長く（128 ビット以上）推測不能な乱数が要る。user_id + 時刻 のような自作は推測される。
ログイン成功時に ID を再発行する攻撃者が事前に用意した ID を被害者に使わせ、ログイン後にその ID でなりすます「セッション固定化」を防ぐ。Django は自動、Express は req.session.regenerate()、PHP は session_regenerate_id(true)。
ログアウトはサーバー側で破棄するCookie を消すだけでは、盗まれた ID がまだ有効。サーバーのセッションストアから削除する。
有効期限を付ける無操作で一定時間（例：30分〜数時間）、絶対時間（例：数日）で失効させる。
URL に入れない?sessionid=… はブラウザ履歴・Referer・ログに残り、漏れる。
パスワード変更・権限変更時に他のセッションを破棄する乗っ取られた後に本人がパスワードを変えても、攻撃者のセッションが残っていては意味がない。

Cookie の属性

セッション ID を入れる Cookie には、必ず次の属性を付けます。

HTTP 応答ヘッダーSet-Cookie: __Host-session=7f3a…; Path=/; Secure; HttpOnly; SameSite=Lax
属性効果外すと
SecureHTTPS のときだけ送るHTTP のリンクを踏ませるだけで、経路上から ID が盗める
HttpOnlyJavaScript（document.cookie）から読めないXSS が1つあれば ID が盗まれ、なりすまされる
SameSite=Lax他サイトからのリクエストには原則付けない（他サイトからのリンクをクリックして来た GET にだけ付く）他サイトに置かれたフォームから勝手に送信される（CSRF）。Strict は外部リンクから来てもログイン状態にならない厳格版
Path=/サイト全体で有効—
__Host- プレフィックス名前の約束。Secure 必須・Domain 指定なし・Path=/ をブラウザが強制するサブドメインから上書きされる余地が残る
Domain（指定しない）指定しなければそのホストだけDomain=example.com と書くと全サブドメインに送られ、1つのサブドメインの穴で盗まれる
🧪体験：Cookie 属性ビルダー

属性を付け外しすると、Set-Cookie ヘッダーの例と、守れていること・危ないことが変わります。

    ✓ Express（express-session）
    JavaScriptapp.use(session({
  name: "__Host-session",
  secret: process.env.SESSION_SECRET,
  resave: false, saveUninitialized: false,
  cookie: { secure: true, httpOnly: true, sameSite: "lax", maxAge: 60 * 60 * 1000 },
}));
    本番はリバースプロキシの後ろにいることが多いので app.set("trust proxy", 1) も必要です。
    ✓ Flask / Django の設定
    Python（Flask）app.config.update(
    SESSION_COOKIE_SECURE=True,
    SESSION_COOKIE_HTTPONLY=True,
    SESSION_COOKIE_SAMESITE="Lax",
)
    Python（Django settings.py）SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SESSION_COOKIE_SAMESITE = "Lax"   # HttpOnly は既定で True
    フレームワークは属性を設定1つで付けられます。確かめ方は、ブラウザの開発者ツール → アプリケーション → Cookie。

    5. CSRF（クロスサイトリクエストフォージェリ）

    何が起きるか

    利用者が銀行サイトにログインしたまま、攻撃者のページを開いたとします。攻撃者のページには、銀行の送金 URL に向けて自動送信されるフォームが仕込まれています。ブラウザは銀行の Cookie を自動で付けて送信するので、銀行から見ると「本人からの正規の送金依頼」に見えます。利用者は何も操作していないのに、送金・メールアドレス変更・パスワード変更・投稿が行われる。これが CSRF です。

    CSRF：ブラウザが Cookie を自動で付けることを悪用する
    攻撃者のサイト
    自動送信フォームaction=銀行の送金 URL
    被害者のブラウザ
    銀行の Cookieログイン中
    銀行
    送金処理Cookie が正しいので実行
    攻撃者は Cookie の中身を知る必要がありません。「被害者のブラウザに送らせる」だけで成立します。

    どう防ぐか

    • SameSite=Lax（前節）：他サイトからの POST には Cookie が付かなくなるので、これだけで大半の CSRF が止まります。Chrome などは未指定でも Lax 扱いにしますが、ブラウザによって挙動が違うので明示的に付けます。
    • CSRF トークン：フォームごとに推測できない値を埋め込み、サーバーで照合する。フレームワークの機能を使う（Django の CsrfViewMiddleware と {% csrf_token %}、Rails の protect_from_forgery、Spring Security は既定で有効、Flask は Flask-WTF、Express は csrf-csrf などのミドルウェア）。SameSite と二重にしておくのが標準です。
    • 状態を変える操作を GET にしない：GET /delete?id=1 は、<img src="…"> を踏ませるだけで実行されます。削除・変更・送金は POST／PUT／DELETE に。
    • Origin／Referer ヘッダーの検証は補助。欠けている場合の扱いが難しいので、単独の対策にしない。
    ⚠️間違えやすい点
    • 「Cookie ではなく Authorization: Bearer … ヘッダーでトークンを送る API なら、ブラウザが自動で付けないので CSRF は基本起きない」。ただしそのトークンを localStorage に置くと、今度は XSS で盗まれます（7節）。
    • 「JSON の API だから CSRF は無い」とは限らない。Content-Type の確認が無いと、フォームから text/plain で JSON らしき文字列を送られることがある。CORS のプリフライトが働く独自ヘッダーを必須にするか、トークンを使う。

    6. 認可の不備：IDOR・権限昇格・マスアサインメント

    OWASP Top 10:2025 の1位は「アクセス制御の不備」です。認証（ログイン）は多くのアプリにありますが、「この人がこの対象にこの操作をしてよいか」の確認は、画面ごと・API ごとに人が書く必要があり、抜けやすい。自動ツールではほぼ見つけられず、設計とレビューで防ぐしかありません。

    データ単位：IDOR（他人の ID で参照）

    何が起きるか：GET /api/orders/1001 で自分の注文が見える。1002 に変えたら他人の注文が見えた。請求書・診療記録・履歴書・メッセージ、どれでも同じです。IDOR と呼びます。

    ✗ 危険な例：ログイン確認だけ
    Python（Flask）@app.get("/api/orders/<int:order_id>")
@login_required
def get_order(order_id):
    row = db.execute(
        "SELECT * FROM orders WHERE id = ?", (order_id,)
    ).fetchone()
    return jsonify(row)
    ログインは確認しているが、「その注文はこの人のものか」を見ていない。
    ✓ 安全な例：所有者条件をクエリに含める
    Python（Flask）@app.get("/api/orders/<int:order_id>")
@login_required
def get_order(order_id):
    row = db.execute(
        "SELECT * FROM orders WHERE id = ? AND user_id = ?",
        (order_id, current_user.id),
    ).fetchone()
    if row is None:
        abort(404)   # 「無い」と「他人の」を区別して教えない
    return jsonify(row)
    所有者の条件を取得クエリそのものに含めると、取得後の if 文の書き忘れが起きません。ORM なら current_user.orders.get(id) のように関連から引きます。

    機能単位：垂直の権限昇格

    一般利用者が POST /api/admin/users/5/disable を直接叩けてしまう。画面に管理メニューが無いだけで、API には役割の確認が無い。対策は、役割の確認をミドルウェアや共通デコレータに集め、ルートごとに宣言することです。

    JavaScript（Express）function requireRole(role) {
  return (req, res, next) => {
    if (!req.user) return res.sendStatus(401);
    if (!req.user.roles.includes(role)) return res.sendStatus(403);
    next();
  };
}
app.post("/api/admin/users/:id/disable", requireRole("admin"), disableUser);
// 既定を「認証必須」にしておき、公開ルートだけ明示的に例外にする（デフォルト拒否）

    項目単位：マスアサインメント

    プロフィール更新 API が、受け取った JSON をそのままモデルに流し込んでいると、{"name": "taro", "is_admin": true} を送るだけで管理者になれます。受け取る項目を許可リストで決める（pydantic／zod のスキーマで余分な項目を捨てる、Rails の Strong Parameters、Django のフォームの fields）。

    🔑覚え方：認可の3原則「一元・拒否・所有」
    1. 一元化：確認処理を1か所（ミドルウェア・共通関数）に集める。あちこちに if 文を書くと必ず抜ける。
    2. デフォルト拒否：許可を書いていないルートは拒否される構造にする。「書き忘れたら通る」は逆。
    3. 所有者条件：データを引くクエリに user_id = ? を含める。取得してから確認、ではなく。

    UUID や長いランダム ID は「推測されにくい」だけで認可の代わりにはなりません。ID はどこかで漏れます（ログ、画面、共有）。

    🛠️実務ではこうする：確かめ方と設計の表
    • 確かめ方：利用者 A でログインしたまま、利用者 B のデータの ID を URL・API に入れる。403 か 404 なら OK。200 で中身が返れば IDOR。一般利用者のセッションで管理 API を叩き、403 になるか。これを自動テストに入れる。
    • 設計の表：設計時に「役割 × 対象 × 操作」の表を作る（例：一般利用者は自分の注文を参照・取消できる、管理者は全注文を参照できるが取消は不可）。表に無い組み合わせは拒否。チェックリスト「設計 d3」。
    • レビューで言う一言：「他の利用者の ID を入れたら、どこで弾かれますか？」

    7. OAuth 2.0 / OpenID Connect / JWT の注意

    「Google でログイン」などの外部認証は OAuth 2.0 と OpenID Connect、API のトークンには JWT がよく使われます。どれも自作せず、実績のあるライブラリか認証サービスに任せるのが前提で、そのうえで次の点を押さえます。

    注意点何が起きるか対策
    署名を検証していない／alg: noneヘッダーの alg を none にした署名なしトークンや、公開鍵を HMAC の鍵として使わせる混同攻撃で、任意の中身が通る検証時に許可するアルゴリズムを固定する。PyJWT jwt.decode(t, key, algorithms=["RS256"])、jsonwebtoken jwt.verify(t, key, { algorithms: ["RS256"] })
    exp（有効期限）を見ていない一度漏れたトークンが永久に使えるexp・iss・aud をライブラリに検証させる
    localStorage に保存XSS が1つあればトークンを全部盗まれるHttpOnly Cookie に入れる（この場合は CSRF 対策とセット）か、メモリ上に短命のアクセストークン＋HttpOnly Cookie のリフレッシュトークン
    失効できないJWT はサーバーに状態が無いので、ログアウトや乗っ取り時に即無効化できないアクセストークンは短命（5〜15分）、リフレッシュトークンはサーバー側で管理し、使うたびに再発行（ローテーション）して失効できるようにする
    中身に秘密を入れるJWT は Base64 で誰でも読めるパスワードや個人情報を入れない。入れてよいのは利用者 ID・役割・期限
    OAuth の state を使わないログインフローへの CSRF（攻撃者のアカウントにログインさせられる）state を毎回生成して照合。公開クライアント（SPA・モバイル）は PKCE を使う
    リダイレクト URI の部分一致認可コードが攻撃者のサイトに送られる登録した URI と完全一致だけ許可する（認可サーバー側の設定）

    8. クリックジャッキングとオープンリダイレクト

    クリックジャッキング

    何が起きるか：攻撃者のページに、あなたのサイトを透明な <iframe> で重ねます。利用者は「プレゼントを受け取る」ボタンを押したつもりで、透明な下のあなたのサイトの「削除」「公開」「送金」ボタンを押しています。対策は、自分のページを他サイトの iframe に入れさせないこと。CSP の frame-ancestors（第3章 5節）か、古いブラウザ向けに X-Frame-Options を付けます。

    HTTP 応答ヘッダーContent-Security-Policy: frame-ancestors 'none'   # 自分のサイト内で iframe を使うなら 'self'
X-Frame-Options: DENY                               # 古いブラウザ向けの保険

    オープンリダイレクト

    何が起きるか：ログイン後の戻り先を ?next= で受け取る機能で、?next=https://evil.example/login を渡され、正規のドメインのリンクから偽サイトに飛ばされます。フィッシングの信頼性を上げる道具になり、OAuth のリダイレクトと組み合わさるとトークンの窃取にもつながります。

    ✗ 危険な例
    Python（Flask）next_url = request.args.get("next", "/")
return redirect(next_url)   # 外部 URL も //evil.example も通る
    //evil.example のようにスキームを省いた形でも外部に飛ぶので、「http で始まらない」の確認では不十分です。
    ✓ 安全な例：相対パスだけ、または許可リスト
    Python（Flask）from urllib.parse import urlparse
next_url = request.args.get("next", "/")
p = urlparse(next_url)
if p.scheme or p.netloc or not next_url.startswith("/") or next_url.startswith("//"):
    next_url = "/"
return redirect(next_url)
# Django なら url_has_allowed_host_and_scheme(next_url, allowed_hosts={request.get_host()})
    戻り先は「自サイト内の相対パス」だけ許可するのが最も簡単です。外部に飛ばす必要があるなら、飛ばしてよいホストを列挙します。

    📝用語の補足
    ソルト
    ハッシュの前にパスワードに付け足すランダムな値。同じパスワードでも違うハッシュになり、事前計算した表が使えなくなる。bcrypt・Argon2 は自動で付ける。
    クレデンシャルスタッフィング
    パスワードリスト攻撃。他サービスから漏れた ID・パスワードの組をそのまま試す。使い回しが原因で1回目に成功する。
    TOTP
    時刻に基づくワンタイムパスワード。認証アプリに表示される30秒ごとに変わる6桁の数字。
    パスキー
    FIDO2／WebAuthn に基づく、パスワードを使わない認証。サイトのドメインに紐づく鍵で署名するので偽サイトでは使えない。
    セッション固定化
    攻撃者が用意したセッション ID を被害者に使わせ、ログイン後にその ID でなりすます攻撃。ログイン時の ID 再発行で防ぐ。
    PKCE
    OAuth 2.0 で、認可コードを横取りされても使えないようにする仕組み。SPA・モバイルアプリでは必須。
    リフレッシュトークン
    短命のアクセストークンを再発行するための長命のトークン。サーバー側で管理し、使うたびに新しいものに替える。

    🧠 想起練習

    本文を見ずに答えを思い出してから、各項目を開いて確認してください。

    認証・セッション・認可の3つの関門が、それぞれ弱いと何が起きるか。
    認証が弱い→他人としてログインされる。セッションが弱い→ログインを飛ばしてなりすまされる（ID 窃取・固定化・CSRF）。認可が抜ける→ログインした人なら誰でも他人のデータ（IDOR・権限昇格）。
    パスワードを SHA-256 でハッシュして保存するのはなぜ不十分か。何を使うか。
    SHA-256 は高速に計算できるため GPU で1秒に数十億回試せる。わざと遅い bcrypt か Argon2id を使う（ソルトは自動）。
    NIST SP 800-63B に沿ったパスワードポリシーを4つ。
    長さ重視（8文字以上、15文字以上推奨、上限64文字以上）／記号・大文字の強制はしない／定期変更の強要はしない／漏えいパスワードリストと照合する。
    ログイン失敗とパスワードリセットのメッセージはどうあるべきか。リセットトークンの条件は？
    「ID かパスワードが違います」「登録があればメールを送りました」に統一し、アカウントの有無を悟らせない。トークンは推測不能（secrets.token_urlsafe）・使い捨て・短命で、DB にはハッシュを保存。
    「5回失敗で30分ロック」の問題と、代わりの対策は？
    わざと失敗して他人を締め出すサービス妨害の道具になる。遅延の増加・CAPTCHA・本人への通知・IP とアカウント両方での制限を組み合わせる。
    多要素認証の3方式を強い順に。最も強い方式がフィッシングに強い理由は？
    パスキー／セキュリティキー（FIDO2）＞ 認証アプリ（TOTP）＞ SMS・メール。パスキーはサイトのドメインに紐づく鍵で署名するため、偽サイトでは使えない。
    セッション ID の扱いで守る決まりを4つ。
    フレームワークに生成させる／ログイン成功時に再発行（固定化対策）／ログアウトはサーバー側で破棄／有効期限を付け URL に入れない。
    Cookie の Secure・HttpOnly・SameSite はそれぞれ何を防ぐか。__Host- は何か。
    Secure＝HTTP で送られるのを防ぐ。HttpOnly＝JavaScript から読まれる（XSS での窃取）のを防ぐ。SameSite＝他サイトから勝手に送られる（CSRF）のを防ぐ。__Host- は Secure 必須・Domain なし・Path=/ をブラウザが強制する名前の約束。
    CSRF が起きる理由と、防ぐ方法3つ。
    ブラウザが Cookie を自動で付けるから。SameSite=Lax、フレームワークの CSRF トークン、状態を変える操作を GET にしない。
    IDOR とは何か。クエリでの防ぎ方と確かめ方は？
    ID を変えたら他人のデータが見える認可の不備。取得クエリに所有者条件（AND user_id = ?）を含める。確かめ方は利用者 A のまま利用者 B の ID でアクセスし 403/404 になるか。
    認可の3原則は？UUID は認可の代わりになるか。
    一元化（ミドルウェアに集める）・デフォルト拒否（許可を書いていなければ拒否）・所有者条件（クエリに含める）。UUID は推測されにくいだけで、認可の代わりにならない。
    JWT を使うときの注意を4つ。
    検証時にアルゴリズムを固定（alg none・鍵混同対策）／exp・iss・aud を検証／localStorage に置かない（XSS）→ HttpOnly Cookie か短命＋リフレッシュ／中身は誰でも読めるので秘密を入れない。
